# Session registry deep dive The session registry keeps a client's session alive across dropped connections. It maps a session id to live state for a grace window, so a reconnecting client resumes instead of starting over. It runs in every gateway instance and stores sessions in Redis. Illustrative component, dated 2026-10-14. A dropped socket does not end the session. It stays resumable for the grace window, 300 seconds by default. ## Parts Five parts. The Registry API is the only entry point. Click a node or card to open its detail. Four functions: `create(clientId)`, `resume(sessionId, socket)`, `touch(sessionId)` and `expire(sessionId)`.
RelationshipsReads and writes the session store. Attaches and detaches sockets through the socket binder. Publishes started and resumed events.
 Key `sess:{id}`. The hash holds client id, state, last seen and version.
LifetimeThe TTL equals the grace window.
 Attaches and detaches the live socket for a session. A session has at most one socket. A background task. It scans the session store, ends sessions whose grace window has passed and emits `session.ended`. Publishes `session.started`, `session.resumed` and `session.ended` to the event bus. ## Session states Three states. Ended is final. A socket is attached to the session. The socket dropped. The session can resume until the grace window passes. The grace window passed, or the client logged out. ## Resume flow
1. Client reconnects and sends its session id. 2. Gateway calls `resume(sessionId, socket)`. 3. Registry reads `sess:{id}` from Redis. 4. If the state is detached and the version matches, the binder attaches the socket, state becomes active, and version increments. 5. Registry publishes `session.resumed` and returns the session. 6. Otherwise the gateway tells the client to start a new session.
## Code The resume path. Read three lines closely: the Redis read, the version guard and the miss path. A network round trip to Redis. The version stops two tabs resuming the same session. Returns undefined when another tab won, which looks like a miss to the caller. ## Configuration | Setting | Default | Meaning | |---|---|---| | `SESSION_GRACE_SECONDS` | 300 | How long a detached session can resume | | `SWEEP_INTERVAL_SECONDS` | 30 | Expiry sweeper period | | `REDIS_URL` | — | Session store location | | `MAX_SESSIONS_PER_CLIENT` | 5 | Oldest session ends when exceeded | The grace window is one global setting. See [known issues](#known-issues). ## Metrics Production, last 7 days. Clients asleep for over 5 minutes resume 0% of the time, the same length as the default grace window. ## Failure behaviour `create` fails closed, so the client gets an error. `resume` returns undefined, so clients start new sessions. Sessions live longer than the grace window. Harmless except for memory. One wins by version. The other starts a new session. ## Decisions Survives deploys and is shared across gateway instances. Compare-and-set on the version. No lock service is needed, and the loser sees a miss. ## Known issues A two-tab conflict looks identical to an expired session in logs. The 5-minute grace window is global. Some tenants want longer. Start with the only entry point. A session with a socket attached is active. Two tabs resuming at once: one wins by version, the other starts a new session.
