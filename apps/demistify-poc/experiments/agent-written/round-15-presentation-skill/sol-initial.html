# Session reconnection Can running work survive a lost connection? Source: `brief.md`. Audience: engineers deciding whether to accept the proposal. Everything below describes supplied design intent and a review finding, not measured or verified behavior. Use a process-local Map to separate session and transport lifetimes. Validate reconnect behavior before deciding persistence separately. This proposal does **not** provide restart durability.

Ownership change

One transport owns one live WebSocket. The socket also owns its session reference. Losing the socket loses that reference. A process-local Map indexes sessions by stable ID. The session owns running work; the transport owns its live WebSocket. Disconnecting a socket should not cancel work.

Reconnect sequence

The Map helps a client reconnect to an existing session while its process remains alive. A process restart loses the Map. Rejecting a missing or expired session must happen **before attachment**. No performance measurements have been supplied.

Expiry review finding

Deleting the entry does not end execution. The local session reference remains, so line 47 still attaches the expired session. Return undefined immediately after deletion. The expired branch must delete the entry **and return**. Removing an index entry alone does not invalidate the local reference. The diff uses display rows starting at 40, including the removed row.

Two options

**Gain:** simple registry and fast local lookup as the design expectation. **Cost:** no restart survival; registry state lives in one process. **Decision scope:** validate network reconnection first. Performance remains unmeasured. **Gain:** the proposed registry survives process replacement. **Cost:** an external dependency and consistency work. **Open boundary:** persistent registry data alone does not establish that running work survives process replacement; that lifecycle needs a separate design and proof.

Proposed acceptance path

1. Fix expiry so an expired entry is deleted and never attached. 2. Disconnect during running work and establish that work continues. 3. Reconnect with the same stable ID and establish attachment to the existing session. 4. Establish that missing and expired IDs are rejected. 5. Confirm the process-local boundary; decide persistence separately. These are proposed validation steps. No execution results or performance measurements were supplied. Accept Option A as a bounded experiment after the expiry correction. Keep persistence as a separate decision informed by reconnect evidence and the required process-replacement behavior.
