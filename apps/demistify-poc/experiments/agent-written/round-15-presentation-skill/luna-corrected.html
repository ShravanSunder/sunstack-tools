# Session reconnection **Decision brief for engineers:** how should a reconnecting client find its running work, and should that lookup survive a process restart? Fix expiry handling first. Then validate reconnect behavior with a process-local registry. Decide separately whether restart survival justifies a persistent shared registry. No performance measurements are supplied. ## Ownership changes The socket holds the session reference. When the socket is lost, that reference is lost too, so the client cannot resume the existing work through a new connection. - **Session:** owns running work. - **Transport:** owns one live WebSocket. - **Registry:** indexes sessions by stable ID. This separates the lifetime of the work from the lifetime of its connection. The proposed registry is a process-local `Map`; a process restart loses it. ## Reconnect sequence The gateway looks up the supplied ID. A missing or expired session is rejected; a live session is reused and attached to the new socket. Losing a socket should not cancel the work. ## Expiry review finding In the illustrative function, the expiry branch deletes the registry entry but falls through and returns that same session. That can attach an expired session. **Return `undefined` immediately after deletion.** The fix belongs before reconnect behavior is validated. After deleting the expired entry, return `undefined` here; do not continue to attach it. ## Two registry options **Gains:** simple and fast to try for network reconnects. **Costs:** entries disappear when the process restarts. It does not provide restart durability. **Tradeoff:** validates reconnect behavior with less infrastructure, while limiting recovery to the current process lifetime. **Gains:** the registry survives process replacement. **Costs:** adds an external dependency and consistency work. **Tradeoff:** supports restart survival, while introducing operational and coordination complexity. ## Decision and boundary First correct the expiry path. Then validate that reconnect attaches a new socket to the existing live session and that socket disconnection leaves work running. Use the process-local registry as the bounded reconnect experiment; make the persistence decision separately. The Map is process-local. **Restart durability is not part of this proposal’s demonstrated behavior.** No performance measurements were supplied, so “fast” is an option’s stated tradeoff, not a measured result.
