The session registry keeps a client's session alive across dropped connections. It maps a session id to live state for a grace window, so a reconnecting client resumes instead of starting over. It runs in every gateway instance and stores sessions in Redis.

The only entry point into the registry. It has four methods:

  • create(clientId)
  • resume(sessionId, socket)
  • touch(sessionId)
  • expire(sessionId)

One Redis hash per session, under the key sess:{id}.

  • Fields: client id, state, last seen, version.
  • TTL equals the grace window.

Attaches and detaches the live socket for a session. At most one socket per session.

A background task. It ends sessions whose grace window has passed and emits session.ended.

Publishes session.started, session.resumed and session.ended to the event bus.

The socket dropped. The grace window is running.

The grace window passed or the client logged out. Final.
Steps as written
  1. Client reconnects and sends its session id.
  2. Gateway calls resume(sessionId, socket).
  3. Registry reads sess:{id} from Redis.
  4. If the state is detached and the version matches, the binder attaches the socket, the state becomes active, and the version increments.
  5. Registry publishes session.resumed and returns the session.
  6. Otherwise the gateway tells the client to start a new session.
A network round trip to Redis. The version stops two tabs resuming the same session. Returns undefined when another tab won. The caller sees a miss, the same as an expired session. Only a client asleep for more than 5 minutes never resumes (0%). Every other cause resumes at 94% or better.

Survives deploys and is shared across gateway instances.

No lock service needed. The loser of a race sees a miss.

In logs, a two-tab conflict looks identical to an expired session.

The 5-minute grace window is global. Some tenants want longer.
