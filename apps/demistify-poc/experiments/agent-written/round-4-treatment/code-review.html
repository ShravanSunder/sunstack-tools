# Resume sessions after socket drops Review of the change "Resume sessions after socket drops", dated 2026-10-14. Audience: the change author and a second reviewer. The change is illustrative. The change fixes resume after network blips but breaks resume after every deploy, because sessions live only in process memory. Two blocking findings: F1 and F2. ## Findings Five findings: two blocking (F1, F2), one nit (F3), one nice (F4) and one question (F5). Line 43 looks the id up in `registry`, an in-memory Map. After any deploy or crash it is empty, so every resume returns undefined and clients start new sessions.
Effect on resumeDeploy resume is 12% before and 0% after this change. Network blip resume goes from 35% to 98%.
 Lines 45 to 47 delete an expired session, but it is still returned and attached on line 48. It should return undefined after deleting. The early return on line 44 drops the miss silently.
Suggested fixLog the session id at debug level so resume misses are visible in traces.
 Line 48, the attach call, keeps the socket swap in one place. The old code scattered it across two call sites. Is the 5-minute grace window in registry.ts configurable per tenant, or fixed? ## How resume works after the change Nodes that match a finding take its tone and open its card on click.
1. The client reconnects and sends its session id. 2. The gateway calls `resume(id)`. 3. `resume` looks the id up in the registry. 4. If found and not expired, the session attaches the new socket and the gateway confirms. 5. Otherwise the gateway tells the client to start a new session. Participants: Client, Gateway, Registry, Session.

Survives restarts and is shared across instances. Adds Redis to every environment and about 2 ms per resume. The reviewers recommend this option. No new state.
