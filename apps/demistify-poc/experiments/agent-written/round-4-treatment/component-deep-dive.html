# Session registry Deep dive for an engineer about to change the session registry. Illustrative component, dated 2026-10-14. The session registry keeps a client's session alive across dropped connections. It maps a session id to live state for a grace window, so a reconnecting client resumes instead of starting over. It runs in every gateway instance and stores sessions in Redis. Registry API is the only entry point: create, resume, touch and expire. Each session is a Redis hash under sess:{id}, with a TTL equal to the grace window. A dropped socket leaves the session detached while the grace window runs. Resume succeeds only when the session is detached and the version matches. ## Parts The registry is five parts around one session store. Click a box to open its card. The only entry point: `create(clientId)`, `resume(sessionId, socket)`, `touch(sessionId)`, `expire(sessionId)`.
RelationshipsReads and writes the session store, attaches and detaches sockets through the socket binder, and publishes started and resumed events.
 One Redis hash per session, key `sess:{id}`. Fields: client id, state, last seen, version. TTL equals the grace window.
Grace windowSet by `SESSION_GRACE_SECONDS`, default 300.
 Attaches and detaches the live socket for a session. At most one socket per session. Background task. Scans the session store, ends sessions whose grace window has passed, and emits `session.ended`.
PeriodSet by `SWEEP_INTERVAL_SECONDS`, default 30.
 Publishes `session.started`, `session.resumed` and `session.ended` to the event bus.
Who publishes whatThe registry API publishes started and resumed. The expiry sweeper publishes ended.
 ## States A session is in one of three states. Socket events and the grace window move it.
A socket is attached. Moves to detached on a socket drop, or to ended on logout. The socket dropped and the grace window is running. Returns to active on a resume within the window. Moves to ended when the window passes. The grace window passed or the client logged out. Final.
## Resume flow The gateway calls `resume` and the registry checks the stored session before attaching the socket. 1. Client reconnects and sends its session id. 2. Gateway calls `resume(sessionId, socket)`. 3. Registry reads `sess:{id}` from Redis. 4. If the state is detached and the version matches, the binder attaches the socket, state becomes active, version increments. 5. Registry publishes `session.resumed` and returns the session. 6. Otherwise the gateway tells the client to start a new session. ## Key code The `resume` function as written. The notes mark the lines that matter. A network round trip to Redis. The version stops two tabs resuming the same session. Returns undefined when another tab won, which looks like a miss to the caller. ## Configuration Four settings. The grace window is global; see known issues. | Setting | Default | Meaning | | --- | --- | --- | | `SESSION_GRACE_SECONDS` | 300 | How long a detached session can resume | | `SWEEP_INTERVAL_SECONDS` | 30 | Expiry sweeper period | | `REDIS_URL` | — | Session store location | | `MAX_SESSIONS_PER_CLIENT` | 5 | Oldest session ends when exceeded | ## Metrics Production, last 7 days. **Resume success by cause of disconnect** ## Failure behaviour `create` fails closed: the client gets an error. `resume` returns undefined, so clients start new sessions. Sessions live longer than the grace window. Harmless except for memory. One wins by version. The other starts a new session. ## Decisions Survives deploys and is shared across gateway instances. Costs about 2 ms per resume. No lock service needed. The loser sees a miss. ## Known issues A two-tab conflict looks identical to an expired session in logs. The 5-minute grace window is global. Some tenants want longer.
