Requirements · Typed Sunstack use from TypeScript

The SDK lets developers and models write normal TypeScript against Sunstack: load an existing project or compose a complete configuration as typed values, check it, run it, and consume typed results. The CLI remains a supported consumer of the same Rust engine.

Two authoring paths, one job

Load existing configs reuses projects without conversion. Express configs as TypeScript removes intermediary definition files when desired. Both serve the same typed-call experience; these are user-facing capabilities, not component boundaries.

What a model should be able to do

The observed pain is this session's example: it imports a pre-copied config literal, while rule entries, matcher definitions and Markdown remain file-referenced. The owner corrected that as insufficient. The desired difference is that authored TS values can contain those definitions, and loaded configs yield usable typed values rather than opaque handles.

Scope and negative space

The scope is an npm TypeScript SDK using the existing Rust engine, its supported evidence and model settings. Rust code may change to expose in-memory inputs while preserving domain types and validation. Existing CLI users, config files and serialized reports are protected. No ast-grep fork, language beyond the pinned engine, mandatory Zod, embedded TS runtime, remote sandbox/service, credential storage format, database, deployment or automatic publication is implied.

Outcome-level evidence must include a real installed consumer, complete inline authoring without definition files, equivalent Rust behavior, compiler rejections and Mac/Linux target observations. Old fixtures and controlled backends prove only what they exercise; provider integration and release installation are separate evidence.
