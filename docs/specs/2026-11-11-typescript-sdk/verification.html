Verification Design · How we will know the SDK works

Prove it from a normal TypeScript program: install the package, author or load a config, call the real Rust engine, and inspect the result. Six checks below cover the important ways this could go wrong.

Six questions the implementation must answer

Does loading keep the config stable?

Try: Load A. Change its definition files to B. Run the held value and an edited copy of it.

Expect: The held value uses A. The copy uses the edit and says it was edited. Only reload uses B. Missing/unreadable inputs return unavailable; malformed inputs return invalid.

Exact cases, real boundaries and wrong-build checks

Will do: Install the candidate SDK and load an existing config from a sibling CWD, with nested relative rule/util references. Capture typed values and source digests, alter definition files, then check/run the retained value, edit a captured rule/filter value in a copied configuration, run that copy, and explicitly reload. Also load missing, unreadable and malformed dependencies; distinguish unavailable from invalid without replacement defaults.

Will see: Expected original dependency contents/base paths and source revisions from R1/R2/R11. Held A uses original bytes; edited A executes the edit with edited provenance; reload sees B. Tampered/malformed provenance is refused, and sources receipt contents cannot override configuration.

Also test unchanged integral-float data in matcher metadata, rule entries and root filters: it keeps file provenance; true numeric/text changes become edited, and adjacent wide integers never collapse. Keep real: Real SDK/native/file acquisition and Rust admission; provider replaced only for deterministic execution comparison. needed: SDK load/snapshot journey; lasting.

Countercase: Wrong build rereads a changed definition or resolves it from ambient CWD. A different valid acquisition implementation passes if the captured values/origins remain correct.

Can I author everything in TypeScript?

Try: Write the complete config: Markdown standard, matcher, evidence kind, filter, questions and decision graph. Run it with no definition files.

Expect: It matches the equivalent CLI fixture’s requests and results. Inline sources have real IDs/content/digests. A definition base outside the target repo still selects the right checked files.

Exact cases, real boundaries and wrong-build checks

Will do: Use the Specification inline example, including a filter, question graph, matcher, inline standard and exact wide limit. Run from a synthetic repository containing checked content but no config/rule JSON/YAML/Markdown definition files. Compare it with an equivalent CLI file fixture. Put the definition base outside the target repository and verify target-root globs/filter folders. Assert root, filter, kind, matcher, utility and Markdown source IDs, normalized content/digests, and inline rather than fictional file origins.

Will see: R3/R5/R7 reference example, existing Rust semantic policy and explicitly equal scripted answers.

Keep real: Real native admission/compiler/executor and evidence parser; controlled backend for exact request answers. needed: complete SDK inline/native parity journey; lasting.

Countercase: Wrong build writes a hidden temporary project, loads a fixture, skips the filter or changes request state. A content-based implementation with no temp files passes.

Do the types and Rust checks catch mistakes?

Try: Compile good and bad callers, then send invalid values through the actual native boundary.

Expect: Wrong typed properties and variants fail compilation. Rust refuses bad references, limits, languages and patterns. u64::MAX round-trips exactly. Upstream wrapper keys stay permissive; nested rule/pattern keys stay strict.

Exact cases, real boundaries and wrong-build checks

Will do: Compile a valid caller and separate wrong-key, wrong-variant/result and numeric cases. Cross-reference closure is a native negative, not a claimed TS rejection. Compile all 29 canonical upstream authored language spellings and separately check snake_case result-language narrowing. Exercise generated 0.13 language, document-field, anchor, native HTML-section and mechanical-tool variants through native execution, including whole-token R1 versus R10, missing/outside-root and unsupported fragments. Enumerate every accepted matcher/utility wrapper field/default against upstream; typed misspellings fail; dynamic unknown wrapper keys are ignored, but dynamic unknown rule/contextual-pattern keys are refused in both paths. Strict Sunstack unknown keys still refuse. For native sections, run the flat Serde selection wire with full/own/enclosing_own fields (top-level parent Absent), asking projection versus raw mechanical markup, constructor refusals and intended compiler diagnostics for mutually exclusive filters. Require actual Invalid and the declared native diagnostic for malformed selectors; unrelated failed/unavailable/cancelled endings must fail the observation. Then send dynamically invalid but structurally well-typed inputs through the real native entry.

Will see: R4/R5/R12/R13/R14 examples and declared limits; compiler rejection must reach intended assertion rather than setup failure.

Keep real: Actual TypeScript compiler, generated exports, native encoder and Rust constructors/reference checks. none: focused compiler/contract/native tests.

Countercase: Wrong build exposes any, enum declarations, unguarded ABI skew, unsafe rounding, or bypasses Rust constructors. Different valid generated syntax passes.

Are check and cancellation safe to compose?

Try: Trap provider/key/checked-file access during check. Overlap two runs and abort one; also abort before dispatch and interrupt a native reply.

Expect: Check has zero such effects. Only the chosen run cancels; its work settles. Pre-abort has no report, partial runs retain actual evidence, and an unknown ending is failed with effects unknown. No whole-run retry occurs.

Exact cases, real boundaries and wrong-build checks

Will do: Observe check on an asking/filter program with provider, credential and checked-target acquisition traps; then overlap two real native calls under causal gates and abort one. Observe all owned work settle and the other remain correct. Include already-aborted input (cancelled/null report), definition-read failure (unavailable/no report), credential/backend/scope/path setup invalid, partial incomplete/cancelled reports and a recoverable unknown native reply. Assert separate diagnostic origin versus checked path on a scope refusal. Assert exact status mapping, retained partial requests/usage and one SDK invocation with no whole-run repeat. Fatal host crashes are not simulated as catchable outcomes.

Will see: R6 zero effects; R8 explicit per-call context and terminal settlement.

Keep real: Real SDK/native scheduling/tokens; controlled external backend only where no hosted-provider claim is made. needed: SDK isolation/cancellation journey; lasting.

Countercase: Wrong build requests a key during check, mutates global CWD, cancels both calls, or returns while native work continues. Different schedulers pass if the invariants hold.

Does the npm package work on Mac and Linux?

Try: Fresh-install the packed candidate in all six OS/CPU/libc cells, without Rust or Zod, and run the same TS program.

Expect: Every cell uses the correct addon. Wrong runtime/platform, missing addon and version skew fail before effects with the documented reason. No optional Zod validator is advertised.

Exact cases, real boundaries and wrong-build checks

Will do: Pack and freshly install the candidate assets on each declared target with no consumer Rust toolchain or Zod. Compile and run the same TypeScript consumer; test unsupported runtime/platform, missing addon and mismatched addon cases against closed failure variants. Assert ContractInfo release/revision/target and that the base export map advertises no Zod entry point.

Will see: R10 six-cell matrix, R13 exact integers, R14 matching release, R15 optional-Zod independence.

Keep real: Real package-manager install, platform loader, addon, compiler and engine. needed: SDK package matrix journey; lasting.

Countercase: Wrong build selects the wrong libc/CPU addon, depends on a workspace file or needs Zod/Rust compilation. Different packaging passes if clean installations work.

Did we preserve the CLI and connect the real provider?

Try: Run existing CLI cases from root and subdirectories, with named paths and all scopes, explicit roots inside/outside a Git workdir and the established no-match/outside-root refusals. Separately run one bounded SDK inference through the ordinary provider.

Expect: CLI target roots, report bytes, meanings and exits remain equivalent. Real request/result evidence proves the host connection; scripted answers cannot substitute for it.

Exact cases, real boundaries and wrong-build checks

Will do: Run the existing CLI verification cases on the integrated engine; compare normalized input/output/report facts, including invocation from a subdirectory with config elsewhere, explicit named paths and default/all/since scopes. Assert scope diagnostics preserve the offending checked path separately from definition origin. Refuse relative SDK roots without CWD access. Preserve the CLI config-derived target root and current diagnostic/report/exit behavior. Run a small SDK inference case through the ordinary existing provider boundary and retain real request/result evidence.

Will see: R7/R9 authoritative CLI outcomes and exact SDK authored request state/questions; current budgets/backend policies.

Keep real: Real CLI/native engine; one separately authorized real provider observation for hosted integration, not scripted answers. existing CLI journeys as applicable plus needed SDK hosted journey; lasting.

Countercase: Wrong build changes CLI bytes/exit meaning, reconstructs/shortens questions in TS, invents usage, or mistakes a fixture reply for hosted proof.

What counts as evidence?

A passing typecheck cannot prove execution. A controlled backend cannot prove provider integration. A Mac result cannot prove Linux. Every declared platform cell and the real-provider observation remain required; missing access leaves that part unverified.

Use the integrated build and retain its source/artifact identity, commands, counts and exits. Distinguish setup failures from intended negative cases. An in-process fatal addon crash can terminate Node; no catchable outcome is promised.

Requirement-by-requirement coverage and proof targets

How each need will be shown

U1 · Load existing configs

Proven by: Load the same project through CLI and SDK and see equal definitions resolved from the original locations.

Still unverified until observed: Filesystem permission/race errors must be exercised; inaccessible dependency is not a loaded pass.

U2 · Use stable loaded values

Proven by: Change the original files, then run the held snapshot and an edited copy: see original A, edited A with edited origins, and B only after explicit reload.

Still unverified until observed: No claim of an atomic filesystem snapshot across concurrent writers; captured content is authoritative after each successful read, with no implicit recapture/retry. Admission rejects inconsistent captured definitions.

U3 · Author the entire definition in TypeScript

Proven by: Author every definition in one typed program and run it where no definition files exist.

Still unverified until observed: Pattern strings/Markdown semantics still need native validation; no full authoring claim from typechecking alone.

U4 · Get concrete types in both directions

Proven by: Compile correct usage and reject incorrect authoring/result usage, then execute the installed consumer.

Still unverified until observed: Generated structural types do not statically prove arbitrary reference closure or constructor predicates.

U5 · Keep Rust guarantees

Proven by: Feed the same valid and invalid definitions through both consumers and observe the same Rust admission decisions.

Still unverified until observed: Do not count a handwritten validator or mocked Rust constructor as parity proof.

U6 · Keep using the CLI

Proven by: Run existing CLI reference cases and retain their established outcomes and report meanings.

Still unverified until observed: Existing CLI proof is reused only when current source/build dependencies match; independent engine changes need their own accepted reference.

U7 · Call the engine from code mode

Proven by: Check without effects, then run explicitly; compare real requests/outcomes and isolate cancellation.

Still unverified until observed: Scripted backend proves mechanics, not hosted integration. Missing credentials leave the real-provider portion open, not waived.

U8 · Use ast-grep typing where it applies

Proven by: Typecheck supported matcher objects and let the actual pinned Rust compiler reject unsupported ones.

Still unverified until observed: No Markdown/JSON grammar maps are currently promised; kind strings remain runtime checked unless supported maps are added and independently validated.

U9 · Install through npm on Mac and Linux

Proven by: Freshly install and run the typed example in every target cell, with no Rust compilation by the consumer.

Still unverified until observed: Every declared OS/CPU/libc cell remains required. Unobserved cells prevent distribution readiness; a static CLI archive is not addon evidence.

U10 · Keep Zod optional

Proven by: Run the base package with no Zod dependency; verify the base export map does not advertise an unshipped optional validator.

Still unverified until observed: No optional validator ships in this design; prototype Zod export failure is not a base-package failure.

Existing test routes and the SDK journeys we need to add

Existing evidence and journey gaps

The project has verify-sunstack-rule. Its current lint/refusal, filter, report, process/cancellation and release routes are reference material for the unchanged CLI boundaries. They do not yet provide complete SDK load/inline/native-install journeys. The paired Verifier must add the lasting SDK journeys before observations rely on them.

The experiment's native tests (historical local reference: /Users/shravansunder/dev/sunstack-tools.experiment-typed-typescript-sdk/packages/typed-sdk-experiment/tests/native-roundtrip.test.ts), compiler test (historical local reference: /Users/shravansunder/dev/sunstack-tools.experiment-typed-typescript-sdk/packages/typed-sdk-experiment/tests/compiler-rejections.test.ts), and tarball consumer (historical local reference: /Users/shravansunder/dev/sunstack-tools.experiment-typed-typescript-sdk/packages/typed-sdk-experiment/scripts/smoke-installed-package.ts) show useful boundary techniques but currently exercise a file-referenced config check and macOS arm64 only. Reuse only their unchanged valid portions; do not promote them to full-run or platform-matrix proof.

Evidence recording, repository gates and provider access

Evidence required before implementation acceptance

Required repository Rust/TypeScript gates remain mandatory. Pin the integrated source, generation inputs, native artifact, package version, runtime/platform, fixtures and backend for each receipt. Record actual test counts and exits, separately retaining setup failures, intended negative results and failed observations. The currently unverified seven-file acquisition delta cannot inherit older passing results.

A real-provider observation requires the existing owner-authorized credential route and bounded synthetic content; no resolved secret enters source, artifacts or generated TS. The Verification Design grants no credential, account, CI or publication authority. CI and target availability are implementation preflight prerequisites, not evidence from this design. Full Linux/Mac proof and real-provider proof may not be silently replaced with stand-ins or waived.

No new benchmark, security certification, inference-quality evaluation or remote sandbox claim is part of this scope. Document authoring is checked with the matching HTML checker; that does not prove the future SDK implementation or visually inspect the pages.
