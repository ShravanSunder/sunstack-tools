Specification · Typed configuration and engine calls

A TypeScript caller can load existing configuration files or supply complete typed definitions. Both forms have the same semantic admission and execution outcomes. Loading and checking never dispatch inference; running is an explicit call. This page defines observable behavior, not internal package ownership.

What each path promises

Consumers and boundary

Local TypeScript execution is the caller's host. No embedded executor, hosted Code Mode sandbox or arbitrary callback execution inside Rust is promised. The caller may compose functions before invoking a data-based API.

R1 · Discover and resolve existing configs

Required: load uses the same explicit-path or upward-discovery behavior as the CLI. It resolves every definition reference from the original declaring config/project directory, not the caller's later CWD. Missing, unreadable, malformed or unsupported dependencies return bounded diagnostics; no default replacement is fabricated.

Basis: U1, U6. Entities: E1, E2.

Proof obligation V1: CLI-equivalent config tree loaded from a different working directory yields equal authored definitions and origins.

R2 · Capture an immutable load snapshot

Required: A successful load returns deeply readonly typed configuration values with captured source content and origins. A copied configuration carries its captured definition values; it does not turn back into file references. The typed value is the execution authority. Original source content is provenance, never a second executable definition. An unchanged captured value retains its file origin and original bytes; a changed value gets an edited origin linked to its original source and a fresh normalized content/digest. Malformed source metadata is refused. Capture is not an atomic multi-file filesystem revision. No old digest authorizes edited values, and no snapshot call rereads a definition file.

Basis: U2. Entities: E1, E2.

Proof obligation V2: Load A, mutate disk to B, then run both held A and a copied A with an actual rule/filter change: the original uses A, the copy uses the edit with edited provenance, and explicit reload uses B. No captured definition is reread.

R3 · Express complete definitions as typed values

Required: Direct authoring supports inline rulebook Markdown with marker-linked typed rule entries, evidence matchers and utilities, evidence kinds/fields, HTML and Markdown document settings, filters and gates, questions/decision graphs, model settings and limits. File references remain permitted. Inline acquisition neither requires nor creates temporary JSON/YAML definition projects.

Basis: U3. Entities: E1, E2, E3.

Proof obligation V3: A complete authored value can be admitted and run with no definition files present; inspected repository content remains a distinct runtime input.

R4 · Constrain input and result shapes

Required: SDK declarations constrain keys, primitive values, nested variants, outcomes and result access. They derive from Rust-owned contracts; no TS enum/const enum or generic any substitutes for a known domain shape. Static shape validation does not claim to prove arbitrary pattern strings, numeric refinements or cross-reference closure.

Basis: U4, U5. Entities: E1, E3, E4.

Proof obligation V4: A valid caller compiles; invented config/result members and wrong discriminants fail. Rust constructors still decide refinements.

R5 · Share semantic admission

Required: Equivalent loaded and directly authored configurations pass the same Rust validation, marker binding, reserved-utility, supported-language, graph and filter-reference checks. Invalid values stay invalid regardless of how they were authored. No second TS implementation decides engine policy.

Basis: U5. Entities: E1, E3.

Proof obligation V5: Parity/refusal examples include unknown fields on strict Sunstack objects (with the upstream wrapper/rule distinction below), invalid globs, zero nonzero limits, missing markers, duplicate IDs and undefined graph/filter references.

R6 · Keep check credential-free

Required: check admits and compiles definitions and returns a typed summary or diagnostics. It performs no provider request, credential-store access, checked-target-file acquisition or lint verdict evaluation. Definitions explicitly referenced by a direct input may be read for admission; loaded snapshots use their captured bytes.

Basis: U7. Entities: E1, E3, E4.

Proof obligation V6: Admission of an asking/filter config succeeds without a key, provider requests or reading checked files.

R7 · Run explicitly and preserve outcomes

Required: run explicitly selects a checked root and scope and invokes the Rust engine. It retains findings, uncertainty, incomplete/cancelled states, exact authored state/questions, usage and request evidence. All eight existing engine statuses have the mapping below. Admission and later operational refusals are typed invalid outcomes. Acquisition failure before a report and cancellation before dispatch carry no fabricated report. Observable unknown endings are typed failed outcomes, with effects explicitly unknown after dispatch. The SDK never retries a whole run.

Basis: U7, U4. Entities: E1, E3, E4.

Proof obligation V7: Equivalent file/inline runs have equal semantic results and requests; force operational invalid, incomplete, pre-dispatch abort, in-flight abort and an unknown native reply, and observe the exact outcome/partial evidence with one SDK invocation and no automatic repeat. Only declared origin/time representations may differ.

R8 · Isolate and settle cancellation

Required: Each check/run owns its cancellation and execution context. Aborting one cannot cancel another or mutate process CWD/environment. An already-aborted signal starts no work. An already-aborted signal takes precedence over encoding/dispatch failures. A live call settles owned local work before returning. Detectable encoding, installation, ABI and native-call failures use the closed failed variants below. An in-process fatal native crash can terminate Node and has no promised catchable exception or returned outcome.

Basis: U7, U5. Entities: E4.

Proof obligation V8: Overlap two calls and abort one at a causal gate; the other retains its own sources, scope and result. Also abort before dispatch and observe cancelled with no report, provider request or owned work. A recoverable lost native reply returns failed with effects unknown, never completed.

R9 · Preserve CLI compatibility

Required: Existing CLI config/report formats, command meanings, source discovery and output/exit semantics remain unchanged. The SDK is an additional engine consumer; Rust is not made to execute arbitrary TypeScript files.

Basis: U6. Entities: E1, E4.

Proof obligation V9: The current CLI regression/reference cases remain equivalent on an integrated build, except independently authorized engine changes.

R10 · Install matching platform artifacts

Required: A documented supported npm/runtime/platform combination installs the correct addon and concrete declarations without consumer Rust compilation. Initial target matrix: macOS arm64/x64, Linux arm64/x64 with glibc and musl. Unsupported combinations fail explicitly. Public publication is a separate owner action.

Basis: U9. Entities: E5.

Proof obligation V10: Fresh installations compile/run the same typed consumer in every declared matrix cell using the packed candidate assets.

R11 · Return source provenance without changing legacy reports

Required: SDK results identify the captured definitions actually used: file origins, inline IDs, or edited origins linked to their baseline, exact captured content and digest. No fictional file is reported as a file that was read. Existing saved CLI report shape/readback remains unchanged. SDK report persistence and migrations are not part of this contract.

Basis: U2, U5, U7. Entities: E2, E4.

Proof obligation V11: Mutating a source file after load cannot alter the returned source content/hash for a snapshot run; an inline origin is visibly inline.

R12 · Bound ast-grep type claims

Required: The SDK exposes the pinned upstream matcher property set below, with all languages accepted by pinned engine 0.15.1. The same upstream decoder/compiler is used for file and typed inputs. Sunstack-owned strict objects retain their existing unknown-field refusal. Upstream ast-grep objects retain the existing decoder behavior: unknown keys on the top-level config/global-utility wrappers are ignored, while nested rule and contextual-pattern objects refuse unknown keys; TypeScript object-literal checking rejects unknown declared properties. Existing accepted metadata/fix/rewriter properties remain accepted, without adding codemod execution. Grammar-specific static kind/field claims require an actually shipped compatible map.

Basis: U8. Entities: E3.

Proof obligation V12: Compile supported property examples, reject misspelled typed object-literal properties, execute both wrapper-level unknown-key inputs (ignored) and nested rule/contextual-pattern unknown-key inputs (refused) through both decoders, and reject unsupported evidence languages. Missing Markdown/JSON grammar maps are not advertised as static kind safety.

R13 · Preserve numeric values

Required: Full-width Rust integer fields use an explicitly lossless TS representation, including bigint for u64. A value such as u64::MAX crosses the call and return exactly; overflow or unsafe numeric encoding is rejected rather than rounded. Nonzero/range and other constructor checks remain in Rust.

Basis: U4, U5. Entities: E1, E4.

Proof obligation V13: 18446744073709551615n round-trips exactly; one greater and zero in a nonzero field are refused.

R14 · Detect incompatible contract versions

Required: The installed declarations, SDK encoder and native contract belong to one pinned release. Calls to an incompatible native contract are refused before engine effects with an actionable compatibility error, rather than being cast into the declared result type.

Basis: U4, U9. Entities: E1, E5.

Proof obligation V14: A deliberately mismatched addon cannot execute provider/engine work or masquerade as a typed successful response.

R15 · Make validation extras optional

Required: The primary SDK import and typed calls require no Zod dependency. This deliverable ships no optional validator entry point. A later Zod proposal must first prove defaults, optionality, numeric representation and generated-type parity; failure leaves that extension unshipped without relaxing the base contract.

Basis: U10. Entities: E1.

Proof obligation V15: A fresh consumer with no Zod installed typechecks and runs the base API. Package exports contain no promised validator entry point; optional-validator execution is not an acceptance gate for this deliverable.

Public behavior and typed outcomes

Shared call/install/provenance obligations have their home under Load existing configs and also serve Express configs as TypeScript. Author-only definition/matcher obligations have their home under Express configs as TypeScript. Names below are the selected callable contract. DTO declarations come from Rust. The adapter lazily loads the native addon on a call, so an unsupported addon is a typed call failure; a package-manager installation failure remains an installation diagnostic. No ordinary domain or detectable native-call ending is thrown into an untyped exception.

Unavailability means an input definition could not be acquired (not found, unreadable or I/O failure), before admission; invalid means acquired input or run setup was refused. Provider and engine work that has partial results uses incomplete, not unavailable. A failed outcome after dispatch says effects are unknown even after local tasks settle; it must not trigger a transparent retry. Fatal process termination is outside returned outcomes.

Loading and editing

A loaded value's configuration is a concrete Configuration whose rulebooks and evidence use captured variants. These include parsed editable values plus original source content for provenance. The parsed value is the only execution authority. On every call Rust parses original content only to compare provenance; equal values retain file provenance, changed values produce edited provenance linked to that file. Malformed originals are invalid, and supplied digests are ignored. No filesystem read is needed for that comparison. sources on LoadedConfiguration is an informational receipt, never executable input; check/run always use its configuration.

For SDK run, root must be an absolute path (relative roots are invalid/unsupported_inputs); it is the explicit checked directory, exactly as CLI --root: canonicalize that directory without widening it to a parent Git workdir. All check.files/check.ignore globs, filter per/reads paths and gitignore behavior are relative to the resulting target root. Optional paths are resolved against the explicit checked root. base_directory resolves definition references only. Default scope selects staged, unstaged and untracked changes; since compares the named revision to the worktree; both require Git. all works without Git. Invalid revisions/paths preserve existing engine refusals. The CLI keeps its current distinct rules: discover config from CWD, derive target root from the config directory's Git workdir (or config directory), resolve explicit target paths from invocation CWD. An SDK run may intentionally select a target repository different from its definition base. Named paths outside root are invalid; named paths selecting nothing are incomplete. A no-named-path empty selection keeps the engine’s nothing_selected outcome. Change scope at an explicit subdirectory root is refused as the engine does; all remains supported. lint cases retains its historical root and refuses --root.

Exact limits of the contract

Config values are data: functions, cycles, promises, symbols and non-finite numeric values cannot silently disappear into JSON. Optional object properties may be absent; invalid array entries and unknown keys in strict Sunstack objects are not normalized into validity. R12 specifies upstream per-object behavior: unknown wrapper keys are ignored, unknown rule/contextual-pattern keys are refused. Per-field Rust admission remains the final authority after lossless transport. IDs/references are checked in Rust; generated Record types alone do not prove that a referenced name is present in the same object.

Node 26 is the initial SDK execution target selected from this repository's pinned toolchain, with a separate compiler invocation for type checking. Running a .ts file is not a typecheck. The new SDK runtime floor does not change the existing CLI package's runtime support.

SDK results carry source snapshots with explicit file, inline or edited origins. This design adds no SDK saved-report writer or persisted-source migration. Existing CLI saved reports and show/cases behavior are preserved; no fake readable file paths substitute for inline sources.

Pinned engine 0.15.1 contracts

Authored matcher language uses the canonical upstream SupportLang serialization spelling (Markdown, TypeScript, CSharp and the other pinned variants), accepted by its decoder. File aliases normalize to that same canonical spelling before captured-value comparisons. Engine result EvidenceLanguage uses its existing snake_case serialization; those are distinct generated unions, not interchangeable aliases. The generated input/result graph includes all 29 language variants, FieldSource.document { path, rule }, typed target anchors found/missing/unsupported, anchor_exists { field } and contains_field { field, needle }. contains_field uses whole-token Unicode boundaries; empty/unavailable needles stay incomplete. Target/document acquisition retains contained/missing/outside-root distinctions, exact file origins and shared budgets. HTML asking text is projected by Rust while mechanical checks retain raw source. None of these are reimplemented in TypeScript.

Public SDK scope uses the engine’s current semantics. Engine 0.15.1 evaluates the model-credential requirement after target/scope selection: an empty scope completes keyless; selected model work still requires a credential; named paths selecting nothing remain incomplete. Recursive JSON metadata numbers use an accurate number/bigint representation, with lossless supported integer bounds; exported declaration/native meaning is guarded by the contract revision. Internal ChangeCaptureRequest calls must supply ContextCapture explicitly: preserve existing caller choices (ChangedOnly for lint selection, Full for connected context). The SDK must not expose an internal context option or silently change capture policy.

Native HTML sections in the current Rust contract

The generated input graph includes native html_units kind matchers, exclusive with rule, inline_rule and markdown_units. Its actual Serde wire is { mode: 'unit', units: ['section'] } with at most one starts_with or pattern filter. Rust rejects empty units, empty prefixes and invalid or empty-matching regexes. It is not the internal Rust enum representation.

The section field source ({ from: 'section', text: 'own' }) uses text: 'full' | 'own' | 'enclosing_own' | 'heading'. A section runs from an h1–h6 heading to the next same-or-higher heading in document order, including wrapped headings. Own text excludes child sections; enclosing own is the direct parent's own text, and is Absent for a top-level section. Native HTML asking views retain standard alt and aria-label tokens and separate element boundaries. Custom attribute text is included only when configured under evidence.html.text_attributes; existing body fields and raw source hashes stay raw. The derived heading field has the explicit contract below. HTML prepared request text/hashes therefore follow the current engine and old HTML answer reuse must be revalidated. Ordinary Markdown asking retains its raw text. Native Markdown units and anchors follow the current contract below.

The integration target is SDK/native release 0.15.1, contract revision 8. Declarations and addon must match; mixed release/revision artifacts refuse before engine effects. These version requirements are a contract, not evidence that a particular candidate passed its installed-package checks.

Native Markdown units and heading anchors

A kind can select markdown_units: { mode: 'unit', units: ['section'] }; the accepted unit names are section, paragraph and list_item, with at most one prefix or regex filter. A rulebook kind accepts unit mode only. Section fields require exactly the section unit. Markdown uses its existing parser ranges: list items clamp, and headings in block quotes do not close outer sections.

Markdown fragment targets resolve inline HTML id/name anchors without a heading scheme. Inferred heading anchors require evidence.markdown.heading_anchors: 'github'; omitted or null means no renderer convention. Without a scheme, an inferred fragment returns { status: 'unsupported', reason: 'heading_scheme_not_configured', fragment }. Unsupported document formats instead return reason unsupported_document. With GitHub configured, duplicate suffixes, image-alt exclusion and the existing Unicode lowercase limit apply; an absent inferred heading is missing. Link fragments percent-decode once. Under path_or_skill, foo.md#x is a path; Demistify island IDs remain outside this contract.

The same typed html and markdown settings belong to every evidence source variant: inline, captured and project. HTML defaults have no custom skipped tags or attribute mappings. skip_tags changes heading membership rather than deleting raw source; template headings remain excluded by the standard behavior. Tag and attribute matching is ASCII case-insensitive. Omitted objects and empty collections use those defaults; null objects or collections refuse. Only the optional heading scheme accepts null. Unknown settings and blank names refuse in Rust; TypeScript string aliases do not prove a nonblank name.

Read heading text as a typed field

{ from: 'section', text: 'heading' } returns the selected native section's own heading as Text. { from: 'enclosing', kind: 'outline', text: 'heading' } returns Texts from the referenced native section kind, in the existing outermost-first order. Membership keeps the existing containment rule, including an equal-range referenced section; it is not a promise of strict ancestors only.

HTML heading values contain visible text after one configured asking projection: tags removed, entities decoded and whitespace folded. Both the raw field value and asking field value contain that derived text; spans still point at the original heading element. Escaped text that becomes <Widget> must survive rather than being parsed as a tag a second time. Markdown retains literal inline syntax and entities, removing ATX leading/optional closing markers or the setext underline; spans retain its heading block. The common budgets and cut states still apply. A bounded empty heading is empty Text; an unbounded recovered HTML heading is Unavailable/unreadable. Existing non-heading fields keep their meaning.

Heading context requires a referenced native HTML section kind or Markdown unit mode with units exactly ['section']. Rust refuses rule/AST/nonsection/mixed references, same_file heading and target as_kind nesting into a heading-bearing kind. Structural TS types constrain known members and literal values; actual references, conditional admission and constructor predicates remain Rust checks.

Optional fields and structured values keep their actual wire shape

Omission and explicit null are separate. Custom present-only fields remain optional but reject null. Upstream matcher defaults retain their own rules: an omitted fixer can serialize as null, while message and severity accept omission with defaults and refuse explicit null. Evidence selection exposes the known noul question shape; arbitrary JSON does not replace its members.

Recursive structured values admit their actual numeric representations, including exact bigint integers and finite number values. Upstream full-width range positions must also remain exactly representable. The declaration and returned object must agree; runtime encoding refuses unsafe numbers, and Rust keeps range, nonzero, reference and pattern checks.

Source identity and exact content

Every authored configuration has a caller-supplied nonempty id; load derives its ID from the canonical root config path; an optional label defaults to that id. Inline rulebooks retain their caller-supplied id. Other inline sources have deterministic IDs: configuration id plus an escaped JSON Pointer to the definition (including matcher/utility/filter names). Their label defaults to that pointer. IDs are unique within the bundle. An edited captured value has an edited origin linking its baseline file/inline locator, so it is never described as the unchanged physical file.

File snapshots hash exact original UTF-8 bytes; inline and edited typed values hash a Rust-normalized serialization at the pinned contract revision: recursively sorted object keys, arrays in authored order, optional omission/nullability follows the pinned Rust serializer, explicit JSON null data is retained, lossless decimal integer tokens, finite floats using the pinned Rust JSON encoder, and UTF-8 strings. The receipt names original_text or normalized_value representation and the acquisition (read during load/call, supplied snapshot, or inline). Supplied file paths identify provenance and never assert a new filesystem read. Capture content is provenance only; any changed executable value produces fresh normalized content and digest. The same native capture owner computes all digests.

Unchanged captured values retain original source bytes and digests across TypeScript numeric spellings: a representable integral float such as 2.0 returns through JS as 2. Rust compares transport-equivalent values without rounding distinct wide integers together. Root provenance comparison includes all document settings with defaults normalized: omitted settings, empty settings and a null heading scheme can retain the original bytes. Changing only skip_tags, text_attributes or heading_anchors must each change root provenance and the actual document behavior. This provenance comparison does not alter the canonical serializer or hash format; actual value changes still have edited provenance.

Accepted matcher properties and compatibility

Matchers expose rule, constraints, utils, transform, language, fix, rewriters, message, note, severity, labels, files, ignores, url and metadata from ast-grep-config 0.51.0. The map key supplies id; inline id remains refused as today. Utilities expose rule, constraints, utils, transform, language and optional arguments; their map key supplies id. All nested rule/fixer/transformation/label/file-glob forms are the pinned upstream forms. Metadata is typed data, not any. Existing file matcher defaults and per-object unknown-key behavior remain upstream behavior: wrapper-level keys are ignored; nested rule/contextual-pattern keys are refused; ordinary TS object literals have no arbitrary-property index signature. Accepted fix/rewriter configuration is not a new Sunstack rewriting API.

SDK transport supports finite JSON data and declared bigint integer fields. A YAML-only metadata value that cannot be represented without loss is an explicit SDK unsupported_inputs diagnostic, not silently dropped or coerced; the CLI YAML path retains its existing acceptance. Parity compares the same representable definitions, with this transport refusal identified separately from semantic admission.
