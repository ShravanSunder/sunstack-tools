Move the browsers into one library-owned reader

Reuse the existing selected reader and schema, move its reusable owners to the library, and make implicit authoring hooks explicit. Keep the app's fixture and archives. A single prepared collection per page is the browser's input; there is no new store or backend.

Proposed public names: ex-requirements and ex-call-stack; stable id required, label optional. Requirements stage follows existing page filename/query behavior; the explicit stage query parameter may select overview/specification/program-design/verification on a non-stage page. Internal picker/related/supporting-call elements are controller implementation, not author-required widgets.

demistify prepare <collection-directory> validates and prepares in place through the existing CLI. Its exported Node function returns prepared HTML/pages without writing, and the caller writes only after complete validation. The optional standalone file set keeps existing names: requirements.html is required; specification.html, program-design.html, verification.html and execution.html are optional until authored. An existing record's kind has its existing canonical owner page. Every .html page in the directory, including extra home/plan pages, receives the derived carrier; its authored content is preserved. The carrier is one direct body child before the closing body tag, outside every ex-document; the version/identity meta is in head. Authored record blocks and body templates remain outside the reviewed ex-document as in the existing pages, so repeated preparation does not change the reviewed document source. One data-ex-records inert block per owner page, including an empty array; no block required on non-owner pages. A page with no later records is valid; a declared dangling edge is invalid. Preparation is idempotent, replacing its own one derived data-ex-design-collection carrier and version/meta rather than accumulating them.

Fixed file names preserve the accepted addresses and avoid a new page-map configuration. The cost is convention in the first public guide; users needing arbitrary filenames would justify a separate contract. This release makes no configurable-name promise.

Render and effect ownership

New lightweight islands in src/islands/ lazy-load the browser controllers, following Explorer's ready/error lifecycle. Browser helpers and views live under src/design-documents/; Node directory access remains in src/node/. Runtime never imports the app, reads Router or fetches sibling facts. Schema and pure projections own validation; controllers own selection; drawers own presentation/lifetime; Comments retains review-source identity. No app-specific source import remains. The drawer exposes a type-only public element contract for show/close/open; no new runtime package dependency.

The per-page prepared input is immutable until prepare/reload. Each mount derives its model from that carrier; do not keep an app module-global singleton that breaks a later collection or reconnect. Missing input/version produces a visible diagnostic and no fixture fallback. A missing call stack is a valid empty state; accessing stack/frame must narrow that state instead of asserting a value.

The new islands synchronously register a load promise with the existing registerReviewSource mechanism BEFORE validating the carrier or importing their controller. Validation occurs inside that promise; success supplies the complete validated prepared-collection source, and missing input, invalid shape or version resolves to the existing failed-source variant while showing the reader diagnostic. The review-document input collector includes ex-requirements and ex-call-stack unconditionally, without a src condition, alongside its existing external Markdown and src-based Explorer inputs. Thus a changed record body or relationship after preparation changes the review revision, while a repeated unchanged preparation does not. Every browser page registers the whole collection, because any document view can show any record; a cross-page fact edit therefore changes every browser page revision. Home/plan pages without a browser keep their ordinary markup-based revision. No generated binding stamp, second identity owner or global fingerprint policy is added.

Before validating and deriving the collection, preparation reuses markdownFileReferences and embedMarkdownFiles on a DERIVATION COPY to retain each local Markdown source used in a record body. Its text and original reference are in the prepared body; missing local files or remote Markdown references fail before any output write. The written authored page keeps its original Markdown src and body templates, unchanged apart from the documented carrier/meta. Later Markdown edits are read again on the next preparation. Inline Markdown remains unchanged. This keeps the actual authored Markdown text inside the same review-source boundary as HTML bodies.

Explicit rich parts and identity

Replace last-paragraph extraction with data-ex-part="rule" on the actual currently displayed conditions paragraph. Add sketch, cases, gaps and procedure at their current source positions. With no part, omit that optional compact fragment and keep the complete source body; never guess a last paragraph. Preparation rejects unknown part names, a part not permitted for its record kind, duplicate same-name parts within a body, and any data-ex-part outside a body referenced by one owning record. These are errors naming the page/record/part, never warnings or inferred defaults. The single-page checker validates local authored record/body/part structure and the versioned prepared carrier; a browser element without valid prepared input reports an error instructing preparation. Preparation owns cross-page relation validation, and the browser repeats version/shape checks before mounting. Keep all original full bodies, including the summary, with their source owner.
