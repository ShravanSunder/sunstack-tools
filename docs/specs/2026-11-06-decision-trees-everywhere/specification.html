Specification: what must be true when it works

This page says what a rule author, an agent and you will be able to see when the work is done. It doesn't say how sunstack is built inside; that's the program design. Each rule below is numbered (R1, R2 …). Each says what you would notice if it were broken.

The five parts and their rules

PartWhat you getRules

trees

For: rule authors, and you. When this part works, every Jev judgment can be drawn as a small tree, and a filter is no longer a single big question.

RuleWhat must be trueYou'd notice it's broken whenFrom
R1A filter (E4) is written as questions and a tree (E2) whose ends are its labels or "unsure". A filter written as one question with no tree is refused when the rulebook loads, with a message saying what to change.A one-question filter still loads, or a tree end names a label the filter doesn't haveU23
R2A filter is judged once per folder per run. Every rule gated on it uses that one result.Two rules in the same folder see different kinds, or the filter is asked twice for one folderU13
R3When a filter's tree ends in "unsure", the rules gated on it don't run in that folder. The folder is listed as skipped, with the route that led there.A rule runs on an unsure folder, or the skip isn't listedU14
R4Every question names the parts of the request it reads. A question that names a part its request won't have, or names none (plain-text instructions), is refused at load.A question reads text it never named, or a typo in a name only shows up at run timeU24
R5Every answer a step's question can give has a route, by question type. A yes/no question routes yes, no and in-between. A pick question routes each label it can pick, plus "not sure enough" when its top label is below the bar. A scale question routes each of its ranges, plus "not sure enough". A step missing one of these routes is refused at load.Some possible answer has no defined endU24
R6A tree can ask several questions and combine their answers only through its steps. Which answer wins is visible in the tree, never inside a question.The combination of two answers can't be read off the treeU23, U24
R7In the ai-tools rulebook, the kind filter and the product-workflow rule are each rebuilt as trees of one-fact questions, and pass an independent decision-model review with no high finding.A rebuilt question still asks two things, or a review finds a high findingU23, U24, U16
R23A tree can check whether the text a question reads was fully collected. That covers the piece itself, and each loaded file or skill's opening inside it: not cut short, not missing, not unresolved. A field that couldn't be collected at all ends the step incomplete, naming it. A rule never passes on a "no" answer about text that wasn't fully collected. That answer ends unsure, because absence wasn't shown.A section whose loaded file was cut before its decisive line passes; a section that loads a skill passes without that skill's text being shownU3, U20, U21, U24
R24A filter reads the named fields it declares from each folder, such as a description and an opening. A request carries only what its questions read. The file or folder's name and location are sent only when a question names them. Anything else stays out of the request and is kept only in the record.A filter can see only the description, or a folder or file name that hints at the answer reaches Jev unaskedU13, U24

proof

For: rule authors, and you. When this part works, anyone writing a rulebook can show a rule works without building their own test tool.

RuleWhat must be trueYou'd notice it's broken whenFrom
R12Sunstack can run a file of cases (E11) through the same path lint uses, with the same surrounding text lint would see: the case's skill folder and the files it loads, at the case's revision. Every case gets exactly one outcome, and every case counts. Scored outcomes are right, false warning, missed, unsure and incomplete. Cases that can't be scored are listed with why: stale, no matching piece, more than one matching piece, or not judged because the filter excluded the folder. The counts are reported per rule or filter, separately.Case results differ from what lint gives on the same text, a case silently drops out of the counts, or the counts are mergedU17, U19, U20, U21
R13A case run changes nothing about what lint warns. It is a tool the author uses before switching a rule on, not a gate inside lint.Lint hides or shows a rule depending on stored case resultsU17, U26
R14Cases name real skill text at a fixed git revision. A case whose text no longer matches its revision is reported as stale, not scored.A made-up or drifted case counts toward a scoreU19
R15Each rule's bars, the probabilities its steps compare, are written in its own tree, and the case report names which bar each result crossed. Each bar's value is recorded beside the development cases that justify it. A rule still on an unassessed starting bar isn't switched on.A bar lives anywhere but the rule's tree, or a bar has no cases behind itU18
R25Before a judged rule warns anyone, its cases meet U17:
  • at least 3 real mistakes, each of which must warn, including the text before a real fix;
  • at least 3 good texts, each of which must pass, including the text after the fix;
  • at least 3 near misses;
  • a held-out set it is never tuned on.
Every wrong warning it once gave on a real skill becomes a case that must pass: unsure doesn't count. A must-warn or must-pass case that ends incomplete, stale, unmatched, ambiguous or excluded by the filter hasn't met its obligation. An invalid or missing reply from Jev counts the same way. Labels come from your own fixes where you made one, otherwise from agents labelling blind, with disagreements sent to you. A rule short of these stays off, with what it lacks listed.		A rule warns with fewer cases, a former wrong warning comes back unsure and is counted fine, or a label came from the rule itselfU17
R26Every bar says which number it reads and how it compares. A yes/no question reads the probability of yes: at or above the yes bar is yes, at or below the no bar is no, in between is unsure, both ends inclusive. A pick question reads the probability of the label Jev selected, which TypeSafe defines as its highest-probability label, against a bar chosen for its number of labels. No result claims to be accurate or calibrated from a probability. Accuracy is claimed only from labelled case counts, within one model version, and no improvement is claimed across two model versions.A bar doesn't say what it compares, one bar is reused across question types, or a high probability is reported as "accurate"U24

agent-use

For: agents running sunstack lint. When this part works, an agent reads a few short lines and opens only what it needs.

RuleWhat must be trueYou'd notice it's broken whenFrom
R16Each warning (E10) is one line: file, line or line range, rule and a one-sentence reason. Related files appear as file:line pointers, not as copied text.A warning prints the judged text or the model's answers inlineU27, U1
R17An agent can ask for one warning's detail (the route, the answers and bars, the pointers) without reading the whole report.Getting detail on one warning needs the full reportU27
R27A saved report (E12) keeps, for every request:
  • the exact state and questions as sent;
  • every answer that came back;
  • the model asked for and the model that answered;
  • the content of every rulebook file used, so the tree and bars behind each result travel with the report;
  • each result's route and any gaps.
From the file alone, anyone can re-check why a pass, warning, unsure, skip or incomplete ended where it did, without asking Jev again, even if the rulebook has since changed. A rule the filter excluded was never asked, so the report says it can't be re-walked.		A result in the saved report can't be explained without re-running, or the answering model is missingU24, U27
R18Skipped folders, unsure results and text not read are listed apart from warnings, each with its reason.An unsure result looks like a pass, or a skip is silentU3, U5
R19The run's status goes to the most serious thing that happened, in this order: invalid input (the rulebook or paths couldn't be used), then cancelled, then incomplete, then failed (an error-severity rule's finding, or warnings past a limit the caller set with --max-warnings), then unsure, then clean. Warnings with no limit set never fail a run. Unsure is its own status, neither clean nor failed, and applies only when nothing above it happened.A run reports failed because of warnings with no limit set, an unsure run reports clean, or unsure hides an errorU4
R20In ai-tools, agents are told to run sunstack lint directly with the repo's rulebook. Nothing between lint and the agent hides or adds results.An agent's instructions point at a wrapper, or a switched-on rule's warnings are hiddenU26
R28The ai-tools rulebook that agents run holds exactly the rules meant to be on: the kind filter, the product-workflow rule and the mechanical description checks. Rules kept for rebuilding later live outside it and can't produce results.A rule meant to be off gives a warning on a direct lint runU26, U10

What this won't do

  • No loops, menus or memory inside a tree. A tree is fixed: it asks its questions and walks its steps.
  • No gate in lint that hides rules based on stored test results.
  • No change to Jev itself, and no new kinds of question.
  • No rebuilding the other eight judged rules here. They stay off until each is rebuilt the same way.
What still needs settling
  • Which names sunstack reserves in a request (R9). This is decided in program design, and must be written down for authors.
  • For the product-workflow rule: one section can contain several procedures, so one answer for the whole section may mix them. Whether a piece should be one procedure rather than one section is a program-design question for R7.
