Program design: which part of sunstack does what

In short:

  • Filters move onto the same tree format rules already use. They declare their own list of labels, and their tree ends in one of those labels or "unsure".
  • Reference: rules and filters gain a reference section, which sunstack copies into every request's state.
  • Collection: a tree can check whether its text was fully collected, and a rule never passes on a "no" about text that wasn't.
  • Output: the human output stops printing request text and gives each line an id. A saved report keeps every request and answer, so any result can be re-checked.
  • Proof: a new sunstack lint cases command runs labelled real cases through lint's own path, with their real surrounding text, and accounts for every case.
  • In ai-tools: the two rules are rebuilt on this, the active rulebook holds only the rules meant to be on, the TS gate is removed, and agents run sunstack lint directly.

Nothing here is implemented. Reviews and the plan come first, then your yes.

What happens when a filter judges a folder

Today (filter_run.rs:73-130, 223-239), each folder gets one request holding one field and the folder's path. One answer is then compared with one cut-off.

Proposed: the request holds the fields the filter declares and its reference, but no folder path. All of the filter's questions go in that one request, and then the tree is walked.

The filter's contract (D3):

  • A filter declares labels, its only possible answers, such as general, role, domain, tool_manual and repo_specific.
  • Every tree ending is {"label": <one of labels>} or unsure. A rule's only_when may name only declared labels. Anything else is refused at load.
  • A question's own options, such as "reusable guidance", are not filter labels and can never be an answer.
  • The outcome is one of three closed shapes: Judged {label, path, answers}, Unsure {step, path, answers} or Incomplete {reason, field?, path, answers}.
  • The gate turns that into Walk, Exclude {label} or Skip {unsure | incomplete, path}.
  • No combined confidence is invented for the final label. Each step's own answer is kept.

What a request carries

Today (decision_walking.rs:162-198), a rule's request carries standard, where, the evidence fields and cut-fields. Fields that couldn't be read are dropped silently.

Proposed: the same, plus reference and unavailable-fields. A loaded file whose opening was shortened keeps its existing opening_cut mark. The line-finder's question rides in the same request, as it does today (rulebook_run.rs:149-165). No second call is made.

Reserved names: these six are reserved. An evidence field or reference entry with one of these names is refused when the rulebook loads (R9). Questions name what they read: an evidence field, or a path under reference (R4, R11).

Never in state: a case's expected answer, spans, hashes, and anything the questions don't read. Those stay in the saved report.

The complete check (D2) is a new mechanical step. It reads one field and answers yes only when all of these hold:

  • the field wasn't cut;
  • it isn't unavailable;
  • every loaded file or skill inside it resolved, with an opening that wasn't cut.

Like every mechanical step, it sends nothing to Jev. A tree uses it before passing on a "no".

What the saved report keeps

Today the report keeps each request's state (evidence_seen) and the answers each walk read. It doesn't keep the questions as sent, answers the walk didn't read, or the model that answered (sunstack-driver facts). The engine already holds all of this internally (RulebookRun.requests).

Proposed: --report <file> writes, beside the usual results:

  • requests: each with its id, its rule or filter, its piece or folder, the exact state, the questions in the order sent, every answer returned, and the requested and resolved model, or why it wasn't sent;
  • rulebook_files: the path and content hash of every config and rule file used, so the tree and bars behind each result are known;
  • on each result: its route, the ids of its requests, and any gap.

Because all of a tree's questions are asked together, a saved report can re-walk any result under a changed bar without asking Jev again. Changed wording or changed evidence needs a fresh run, and the report says so.

How a case run works

This path is new. It has no predecessor in sunstack; today it lives in ai-tools' TS runner.

A case file (D4) holds:

  • Rule cases: {kind: "rule", rule, file, revision, lines, text_sha256, expected: "warn" | "pass", set, label_from: "owner-fix" | "blind-agents"}.
  • Filter cases: {kind: "filter", filter, folder, revision, reads_sha256, expected_label, set, label_from}.
  • The rule's bars as recorded beside the development cases that set them: bars: [{step, value, set_from: [case ids]}] (U18).
  • An optional repository path, for cases from another local checkout (U19).

The surrounding text: for each revision, the run copies every file the rulebook checks as it was at that revision (with git archive), then puts today's rulebook files on top. A case therefore sees its own skill folder, that folder's SKILL.md for the filter, and the files it loads, all from the case's revision.

Matching: each case gets exactly one outcome.

  • A rule case matches that rule's results whose piece overlaps its lines in its file:
    • none → no matching piece;
    • more than one → more than one matching piece;
    • excluded by the filter → filter excluded;
    • otherwise its result is scored against the expected one: right, false warning, missed, unsure or incomplete.
  • A filter case is scored right, wrong label, unsure or incomplete.
  • Every case appears in the counts or in the listed cases, never neither.
  • If a rule's current bars differ from its recorded bars, the run says the bars are unassessed (U18).

It writes nothing that lint reads.

Today's version as the baseline: 0.8.0 refuses today's filter shape, so the old rules can't run through lint cases. Instead, the verify driver runs the released 0.7.1 binary with ai-tools main's rulebook on the same temporary trees. It applies the same matching to 0.7.1's JSON report. The comparison names both engine versions and the model each run resolved to.

The two rebuilt trees in ai-tools

These are shapes, not final wording. Each question is written once from the standard and your U16 rulings. An independent decision-model review checks the tree. Bars are set on the development cases (U18), then the frozen tree is proven once on held-out cases. There are no wording rounds.

Kind filter

Jev is shown each skill's description and the opening of its SKILL.md body. It also sees a reference holding the five kind definitions and worked examples. It isn't shown the folder name. Both questions go in one request.

Statistic: both questions read the top label's probability among 3 labels. A bar of p, for example, means a confidence of (p − 1/3) ÷ (2/3), which is not accuracy. The bars start at the engine's usual 0.6 for a pick question and are set on the development cases; a starting bar never switches the filter on. Q2's answer is read only when Q1 picked "reusable guidance"; otherwise it's asked but unused.

Product-workflow rule

Jev is shown each section's body, heading and headings, plus the opening of each file or skill the section loads. The reference holds your U16 rows as worked examples, each with its answer and why.

Statistic: Q1 and Q2 read the probability of yes. At or above the yes bar is yes, at or below the no bar is no, both inclusive, and in between is unsure. Bars start at the engine's usual 0.7 and 0.3 and are set on the development cases. The line-finder reads its top line's probability against its own bar, and that only places the warning's line; it never decides pass or warn.

Policy: a warning needs Q1 yes and Q2 no. The warning is worded as a nudge, because the text can show a product's procedure but can't settle where it belongs. A "no" from Q1 passes only on fully read text. Any in-between answer is unsure. A field that couldn't be collected at all ends incomplete.

This keeps the current rule's two-question shape and fixes the review's findings:

  • It sees the content of loaded skills, not only loaded files, and it never passes on text it didn't fully read (F1, D2).
  • Its second question is a separate fact, so it can't contradict the first (F3).
  • Each question stands on its own. Jev answers both in one request without seeing the other's answer, so neither refers back to the other.
  • Its line-finder uses the same boundary as Q2 (F6).
  • The toolkit's shared tools are part of Q1's definition, through the reference examples, not a separate escape route.

What changes in ai-tools

  • Rulebook:
    • The kind filter and the product-workflow rule are rebuilt as above, with their reference.
    • The skill evidence kind gains an opening field for the filter, and section targets resolve skills to their openings.
  • Active rules only (D7): the config lists rulebook file pairs, and each pair's markers bind to its entries. So:
    • The general-skill pair keeps only the product-workflow rule. The two other judged rules' entries move to rules/held/, and their <!-- K… --> marker comments come out of general-skill.md, recorded in the held file beside the sentence each belongs to. The sentences themselves don't change.
    • The descriptions pair keeps its three mechanical checks, and its two judged rules move the same way.
    • The three pairs whose rules are all judged leave the config. Their files stay as they are.
    Bringing a rule back means moving its entry and marker back.
  • Cases: the existing real scenarios for these two become case files, in development and held-out sets. Their labels come from your fixes or blind agent labels. The held-out cases stay unseen until the frozen run.
  • Removed: the adoption gate (adopted.json, floors, held-back custody, adoption.ts, scenario-adoption.ts, adopt-rule-scenario.ts) and the rules wrapper command.
  • Agents: AGENTS.md tells agents to run sunstack lint --config plugins/skill-authoring/skills/domain-skill-crafting/rules/skill-rules.config.json [paths], adding --report when they want detail.
  • Skills:
    • domain-decision-models: its state and examples line changes, its worked trees show these two trees, and its driver facts name 0.8.0.
    • skill-rules: teaches filter labels and trees, reference, the complete check and case runs.

Assumptions this design rests on
  • A rule's questions about one piece, including the line-finder, already go in one request (rulebook_run.rs:149-165). Filters copy that.
  • Lint can run on a temporary tree that holds the rulebook's checked files at a revision, with today's rulebook files on top. The case run's first step checks this.
  • The released 0.7.1 binary stays available for the baseline run.
  • Both the Jev Advisor and the reviewer put examples in request state. TypeSafe's State page allows it. Neither source claims it makes answers steadier, so only the held-out run speaks to that.
