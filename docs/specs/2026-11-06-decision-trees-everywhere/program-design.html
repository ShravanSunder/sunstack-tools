Program design: which part of sunstack does what

In short: filters move onto the same tree format rules already use, with their own kind of ending: a label instead of pass or warning. Rules and filters gain a reference section, which sunstack copies into every request's state. A question that needs text the request doesn't have ends as a gap, not a pass. The human output stops printing request text and gives each line an id, so an agent can ask for one line's detail. A new sunstack lint cases command runs labelled real cases through the same path lint uses. In ai-tools, the kind filter and the product-workflow rule are rebuilt on this, the TS gate is removed, and agents run sunstack lint directly.

Nothing here is implemented. Two reviews and the plan come next, then your yes.

What happens when a filter judges a folder

Today (filter_run.rs:73-130, 223-239): one request per folder, holding one field and the folder's path. Then one answer is compared with one cut-off. Proposed: the request holds the fields the filter declares and its reference, but no folder path. All the filter's questions go in that one request, and then the tree is walked.

What a rule's request carries

Today (decision_walking.rs:162-198): standard, where, the evidence fields, and cut-fields. Fields that couldn't be read are dropped silently. Proposed: the same, plus reference and unavailable-fields. Before a question is used, the walker checks every field it names. If one is unavailable, the result is incomplete, naming that field.

How a case run works

This path is new. It has no predecessor in sunstack; today it lives in ai-tools' TS runner.

It writes nothing that lint reads. It uses the rulebook as it is now against the case texts as they were at their revisions, which is what an author wants: does today's rule get these real cases right?

The two rebuilt trees in ai-tools

These are shapes, not final wording. Each question is written once from the standard and your U16 rulings, checked by an independent decision-model review, and proven once on held-out cases. There are no wording rounds.

Kind filter

Jev is shown each skill's description and the opening of its SKILL.md body, plus a reference holding the five kind definitions and worked examples. Jev isn't shown the folder name. Both questions go in one request.

Product-workflow rule

Jev is shown each section's body, heading and headings, plus the opening of each file or skill the section loads. The reference holds your U16 rows as worked examples, each with its answer and why.

This keeps the current rule's two-question shape and fixes the review's findings:

  • It sees the content of loaded skills, not only loaded files (F1).
  • Its second question is a separate fact, so it can't contradict the first (F3).
  • Its line-finder uses the same boundary as question 2 (F6).
  • The toolkit's shared tools are part of question 1's definition, through the reference examples, not a separate escape route.

What changes in ai-tools

  • Rulebook: the kind filter and the product-workflow rule are rebuilt as above, with their reference. The skill evidence kind gains an opening field for the filter. Section targets resolve skills to their openings.
  • Cases: the existing real scenarios for these two are converted into case files, in development and held-out sets. The held-out cases stay unseen until the frozen run.
  • Removed: the adoption gate (adopted.json, floors, held-back custody, adoption.ts, scenario-adoption.ts, adopt-rule-scenario.ts) and the rules wrapper command.
  • Agents: AGENTS.md tells agents to run sunstack lint --config plugins/skill-authoring/skills/domain-skill-crafting/rules/skill-rules.config.json [paths], with --report when they want detail.
  • Skills:
    • domain-decision-models: its state and examples line changes, its worked trees show these two trees, and its driver facts name 0.8.0.
    • skill-rules: teaches filter trees, reference and case runs.
  • The other eight judged rules leave the config, with their entries kept for rebuilding later.

Assumptions this design rests on
  • A rule's questions about one piece already go in one request, and the line-finder adds a second. Filters copy the first half of that.
  • Lint can run on a temporary tree holding the current rulebook files plus case texts. If the evidence loader turns out to need the real repository root, case runs need a different way to read case text. That is checked first in the plan.
  • The Jev Advisor's answer on where examples belong was still pending when this was written. The reviewer and TypeSafe's State page both put them in request state.
