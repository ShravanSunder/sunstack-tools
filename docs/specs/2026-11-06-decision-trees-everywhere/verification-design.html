Verification design: how we'll know it works

For each requirement: what will be done, and what will be seen. Nothing here has been run yet; this is the plan for proof. Most of it is checked by engine tests with scripted Jev answers, which prove the mechanics but not judgment quality. How well the rebuilt rules judge is shown on real cases with real Jev: first the development cases, where the bars are set (U18), then one frozen held-out run. Neither proves quality on every skill; they show it on these cases.

A rebuilt rule goes into the config as a warning only when all four hold:

  1. Its development cases meet U17: at least 3 real mistakes, 3 good texts and 3 near misses, with a held-out set kept apart. A rule short of these stays off, with what it lacks listed.
  2. Its bars are set on the development cases and recorded beside them (U18). Its questions are written once from the standard, not reworded to fit.
  3. With everything frozen, every development real mistake warns, including the text before a real fix. Every good text and quiet near miss stays quiet, including the text after the fix.
  4. The frozen held-out run gives zero false warnings, and every real mistake in it warns. No result is left incomplete by the engine itself.

Unsure on a quiet case is allowed; unsure on a real mistake is not. This follows U17 and your ruling to warn only when sure ("details in file, warn if true", 6 Nov). The product-workflow rule's held-out set holds only quiet passages today, so for that rule the held-out run can show only that it stays quiet. Its catching of real mistakes is shown on the development cases.

The kind filter is switched on when its held-out folders give no wrong kind. Unsure is allowed, since it skips and lists the folder (U14).

Proven by

Proven by: a rulebook with a one-question filter is refused, and a filter written as a tree loads. The kind filter then judges every ai-tools skill folder once, ending in a label or unsure, with the route kept for each.

Unverified: trees with many levels; only two-level trees are tried.

Proven by: an independent decision-model review of both rebuilt trees finds no high finding. Rulebooks that miss a route, or name text a question won't have, are refused.

Unverified: whether the questions are well worded is judged by the review and the held-out run, not by a test.

Proven by: a lint run's saved report shows each request carrying the rule's reference unchanged under reference. A clashing name is refused, and an oversized one is reported as too large.

Unverified: whether examples in state make Jev's answers steadier; TypeSafe doesn't claim it. Only the held-out run speaks to it.

Proven by: running the exact command AGENTS.md gives, on ai-tools skills, shows the switched-on rules' warnings with nothing in between. No reference to the old wrapper remains.

Unverified: other repositories; the command is generic, but only ai-tools is run.

Proven by: the human output on a real run has one short line per warning, unsure or gap, with file:line and an id, and no section text. lint show on one id returns just that entry.

Unverified: how agents use it day to day.

Proven by: both skills read as R21 and R22 say, with no line saying examples belong only in the question or teaching a one-question filter. The ai-tools skill tests pass.

Unverified: whether a fresh agent follows the skills well; behaviour tests are out of scope here.

Proven by: with scripted answers, each folder gets exactly one filter request, every gated rule in it reads that one result, and an unsure folder's rules don't run and are listed with the route.

Unverified: none beyond the scripted answers; the held-out run covers real answers.

Proven by: rows 1 to 9 through the product-workflow rule. Real cases for each give the result in your table on the development cases, with zero false warnings on the held-out run. Row 10 through the kind filter: a product's own skill comes out as a tool manual or repository-specific and isn't judged.

Unverified: row 11, a description naming products. That's the description rule's job, and it stays off in this design. Row 12 has no real case yet, and mixed sections are tested only where the cases have them.

Proven by: the same text gives the same result through lint and through lint cases. A case whose text changed is listed as stale. The report names the bar each result crossed, and lint's output is the same before and after a case run.

Unverified: case files in other repositories.

Proven by: a section that loads a missing skill ends as a gap naming the field, never a pass. The run status follows R19's order, through the existing status tests plus one case where unsure and an error happen together.

Unverified: nothing beyond the listed cases.

U2, U6 to U12, U15, U20 and U22 aren't changed by this design. Their existing proof stands.

What the scripted-answer tests don't show

Scripted answers prove that sunstack builds, walks and reports correctly. They say nothing about whether Jev answers the questions well. Only O7 (the review) and O8 (the frozen held-out run with real Jev) speak to judgment. O8 runs once. If it fails, the rule stays off, and the next attempt needs fresh held-out cases. There is no rewording against the same cases.
