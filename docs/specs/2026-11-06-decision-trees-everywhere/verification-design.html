Verification design: how we'll know it works

For each requirement: what will be done, and what will be seen. Nothing here has been run yet; this is the plan for proof.

  • The mechanics are mostly checked by engine tests with scripted Jev answers. They prove the mechanics, but not judgment quality.
  • How well the rebuilt rules judge is shown on real cases with real Jev. First come the development cases, where the bars are set (U18). Then comes one frozen held-out run, compared with today's version.
  • Neither proves quality on every skill; they show it on these cases, for the model version that answered.

A rebuilt rule goes into the config as a warning only when all five hold:

  1. Its development cases meet U17:
    • at least 3 real mistakes, 3 good texts and 3 near misses;
    • a held-out set kept apart;
    • labels from your own fixes where you made one, otherwise from agents labelling blind, with their disagreements sent to you.
    A rule short of these stays off, with what it lacks listed.
  2. Its bars are set on the development cases and recorded beside them in the case file (U18). Its questions are written once from the standard, not reworded to fit.
  3. With everything frozen, on the development cases:
    • every real mistake warns, including the text before a real fix;
    • every good text passes, including the text after the fix;
    • every former wrong warning on a real skill passes. Unsure doesn't count for these.
  4. The frozen held-out run gives zero false warnings, and every real mistake in it warns.
  5. No result is left incomplete by the engine itself.

Unsure is allowed only on a quiet near miss; it is never allowed on a real mistake or a must-pass case. This follows U17 and your ruling to warn only when sure ("details in file, warn if true", 6 Nov). The product-workflow rule's held-out set holds only quiet passages today, so for that rule the held-out run can show only that it stays quiet. Its catching of real mistakes is shown on the development cases.

The kind filter is switched on when its held-out folders give no wrong kind. Unsure is allowed there, since it skips and lists the folder (U14).

Proven by

Proven by: a rulebook with a one-question filter, or a filter ending in a label it didn't declare, is refused. A filter written as a tree loads. The kind filter then judges every ai-tools skill folder once, ending in a declared label or unsure, with the route kept for each.

Unverified: trees deeper than two levels.

Proven by: an independent decision-model review of both rebuilt trees finds no high finding on questions, state, statistic, policy or proof. Rulebooks that miss a route, name text a question won't have, or leave a bar without its comparison are refused.

Unverified: wording quality beyond what the review and the case runs show.

Proven by: a saved report shows each request carrying the rule's reference unchanged under reference. A clashing name is refused, and an oversized one is reported as too large.

Unverified: whether examples in state make Jev's answers steadier; TypeSafe doesn't claim it. Only the case runs speak to it.

Proven by: running the exact command AGENTS.md gives, on ai-tools skills, shows the switched-on rules' warnings with nothing in between. Only the intended rules can produce results, and no reference to the old wrapper remains.

Unverified: other repositories; the command is generic, but only ai-tools is run.

Proven by: the human output on a real run has one short line per warning, unsure or gap, with file:line and an id, and no section text. lint show on one id returns just that entry. From the saved report alone, five kinds of result can each be explained.

Unverified: how agents use it day to day.

Proven by: both skills read as R21 and R22 say. No line says examples belong only in the question, and none teaches a one-question filter. The ai-tools skill tests pass.

Unverified: whether a fresh agent follows the skills well; behaviour tests are out of scope here.

Proven by: with scripted answers:

  • each folder gets exactly one filter request;
  • every gated rule in it reads that one result;
  • an unsure folder's rules don't run, and the folder is listed with its route.

Then the kind filter's case run with real Jev.

Unverified: none beyond the cases.

Proven by: rows 1, 2 and 4 to 9 through the product-workflow rule. Real cases for each give the result in your table on the development cases, and the held-out run gives zero false warnings. Row 10 through the kind filter: a product's own skill comes out as a tool manual or repository-specific and isn't judged.

Unverified:

  • Row 3, a labelled example: it has no real case yet, so it needs one before it counts as covered.
  • Row 11, a description naming products: that's the description rule's job, and it stays off.
  • Row 12 has no real case yet.
  • Mixed sections are tested only where the cases have them.

Proven by:

  • The same text gives the same result through lint and through lint cases, with the case's real skill folder and loaded files around it.
  • Every case is counted or listed with why.
  • A planted always-unsure rule fails the must-warn and must-pass cases.
  • A changed bar shows as unassessed, and a drifted case is listed stale.
  • Lint's output is the same before and after a case run.

Unverified: case files in other repositories.

Proven by:

  • A section loading a missing skill ends incomplete, naming it.
  • A section whose loaded file was cut, answered "no", ends unsure, never pass.
  • A warning reads as a nudge to read and decide.
  • The run status follows R19's order, including one case where unsure and an error happen together.

Unverified: nothing beyond the listed cases.

Proven by: sunstack lint --rules on the final config lists the kind filter, the product-workflow rule and the three mechanical checks, and nothing else. With scripted answers, no held rule produces a result.

Unverified: none.

U2, U6 to U9, U11, U12, U15 and U22 aren't changed by this design. Their existing proof stands.

What the scripted-answer tests don't show

Scripted answers prove that sunstack builds, walks and reports correctly. They say nothing about whether Jev answers the questions well. Only O7 (the review) and O8 (the development and frozen held-out runs with real Jev) speak to judgment. The held-out run happens once. If it fails, the rule stays off, and the next attempt needs fresh held-out cases. There is no rewording against the same cases. A high probability on one answer says nothing about accuracy; only the case counts do, for the model version that answered.
