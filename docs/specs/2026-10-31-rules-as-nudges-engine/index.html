Rules as nudges: the engine

The engine half of the accepted "rules as nudges" design. sunstack lint 0.6.0 tells the agent running a rule what it saw, on which line, how it was decided, and where else to read; and it checks JSON files, so the rule files themselves get rules. Every change is additive: a field a report carries today keeps its name and meaning, warn stays the nudge, and the engine still knows nothing about skills.

One nudge, before and after

Line 17 of ops-observability-stack/SKILL.md, the placement rule's nudge on the signed 0.5.0 engine and in the design.

The agent gets the line, whether a model's answer decided it, and the places to read before it decides: the standard that makes this a concern and the file the section loads. A place the run never read never appears as a link.

What the report gains

FieldOnTells the agentNeed
line, anchorfindingthe line the nudge is about; resolved when Jev picked a line inside the section, default when it fell back to the section's startU2
relatedfindingthe standard's own line first, then the places the run read: loaded files, the heading; SARIF carries them as related locationsU1
basisfinding, every result rowmechanical, or judged when any step on the path read a model's answerU4
answers, pathresult rowsthe answers the walk actually read and the steps it took, passes and gate drops includedU3
cut, opening_cutresult rows, targetswhich fields the model saw shortened, so a cut shows as a gap and not as "fine"U5

Three changes sit behind the report rather than in it: a section's loads are the loads in its own text, not its child sections' (U6); a rule can ask for the full enclosing section or a loaded file's fields (U7, sequenced last because no accepted rule needs it yet); and lint reads JSON evidence, with --check refusing a yaml field on a JSON kind (U8). Severity, status and exit codes don't change (U9).

Where each change lands

Blue is sunstack-evidence, amber is sunstack-rules, teal is sunstack-lint. Each change is an addition to the part that already owns it. The decision walk owns what a result is and how it was reached; piece building owns what a piece holds; the report projection owns what readers see. The line locator is an ordinary Choice question built for each piece, so the decision crate doesn't change.

Line 17's path through the engine

Still one request per piece: the locate question rides along with the rule's own questions. An answer outside the section, or a section longer than the locate limit, keeps the section's first line and says default; it is never an error.

A plan; nothing has run yet. Two existing journeys are extended, the plan writes focused tests, and one keyed check runs once.

U10's known-good reference is the signed 0.5.0 binary's report on the same fixture and answers: every field it carries must read the same in 0.6.0.

The independent review of these four documents is next; after it, Gate 1 accepts both designs at named revisions. Whether Jev picks the right line across many skills is for the placement rule's labelled cases in the skills pull request, not this engine change.
