# Proof design

This plans how [U1–U5](requirements.md#people-and-outcomes) and [R1–R10](specification.md) will be checked through the [owned seams](program-design.md#obligation-trace). It records no observations.

## What the owner will see proved

- **U1 — Choices:** click the Markdown body to select an answer, use the circular details action without changing that answer, and read cards, selectable table rows and local inline details correctly on desktop and phone. Unsupported title/content remains visible as an error. WebKit and physical touch remain outside the planned browser coverage.
- **U2 — Comments:** comment on an item and exact text, reopen the same revision, and carry the same identified comments and selected answers. Failed storage/clipboard and changed-source cases must be visibly honest. Multi-tab editing and cross-revision relocation are not claimed.
- **U3 — Web Components:** use two independent plain-HTML consumers, reconnect the elements, inspect a copy and return from fullscreen without duplicate controls, coupled radio groups or lost original state. A React/Vue adapter is not claimed.
- **U4 — Skills/usability:** fresh agents load each actual candidate guide/workflow and produce usable new pages, while an explanation-only request remains an explanation. These runs establish named examples, not a causal improvement over prior wording or installed implicit routing.
- **U5 — PR readiness:** the complete integrated source passes the repository's required checks and independent review, and both source PRs show current GitHub gates while remaining unmerged. Deployment/cache refresh/package-version consumption remain separate.

## Shared observations

**O1 — Permanent feature fixture.** Add one compact authored page containing a single choice, independent multiple choices, a `view="table"` choice and a `details="inline"` choice, rich body text/link, actual detail diagram, an explicit comment target and cross-block selectable text. Observe actual table structure/row selection/local phone scrolling and inline reveal/close with no sidebar or outline mutation; merely rendering the default cards cannot establish these variants. Keep the real built library, source carriers, native controls, diagram engine, local persistence and review serialization in the path. The existing frozen browser harness serves the whole exact distribution; do not add another driver. Automated native interactions keep their real handlers, including repainting the clicked Comment SVG. Direct host CUA covers visual readability, actual text dragging, clipboard/download where the harness cannot establish the final transferred content, and the 390px layouts. Equivalent successful automated evidence is reused rather than repeated for independence alone.

**O2 — Boundary and failure cases.** Focused tests exercise the single review schema, canonical anchor projection/matching, wrong identity/version, duplicate/malformed ranges, storage read/write failure and envelope contents. A real component fixture rejects missing/duplicate public authoring identities and proves detached-icon event handling, reconnect, original/copy radio isolation and fullscreen return. At wide and narrow widths, replace Comments with Details and back, enter fullscreen from active Comments, and disconnect an older controller after another panel has opened; assert the correct active panel, trigger, restored content and focus. At phone width, the native modal makes underlying pointer actions unreachable: exercise the replacement-owner seam through a clearly labeled component-integration call to the existing action, not as a claimed user click through a modal. Keep reachable wide pointer replacement and phone C replacement, Close/Escape and successful saved-anchor reveal as native user journeys; successful phone reveal exposes the source by closing its sheet, while an unavailable source leaves its refusal readable. Test expectations come from the specification rather than the implementation under test.

**O3 — Fresh authors.** Each named skill has a distinct accepted spec. Freeze matching source-preview guide/runtime and candidate text before giving a fresh worker a realistic task without exposing checks or test framing. One task exercises API retrieval/application; another exercises workflow composition/retrieval; a near-miss checks recognition. Record actual loaded files and actions and manually inspect outputs. Use separate proof IDs so test comments cannot touch owner previews. No installed-cache mutation is needed for candidate application proof. If actual action records or a candidate offering cannot be retained, report the exact narrower claim or gap rather than substituting the worker's summary.

**O4 — Delivery gates.** Reuse the actual root scripts and permanent Node/built-browser harness, authored-page checker, release-intent and Changesets checks. Product source needs a real minor Changeset and keeps the consumed version unchanged; the workflow source needs a coordinated plugin bump/changelog. Independent design, implementation and two one-skill reviews consume the same current source and evidence. PR preparation inspects checks, comments, threads, body, head/base and mergeability; publishing code is not release proof.

## Apparatus and boundaries

The current canonical `.agents/skills/verify-demistify` covers built-runtime launch, Markdown, navigation, inspection and small parts. Its choice/comments journey is **needed**, not already established. The verification owner maintains that recipe and its supported journey reference; the implementer owns product tests. The existing Node/browser configs, frozen-fixture server and fixture-readiness helper remain authoritative.

Root keeps sole host-browser control unless explicitly handed off. Product and authoring workers use separate source/proof write sets. Browser snapshots and comment storage have separate test identities. Storage failure cases are isolated from owner data. Owned servers/tabs are cleaned up after evidence is retained. WebKit, physical touch, file-origin/offline behavior, multi-user/multi-tab collaboration and framework-specific adapters remain explicit limits, not substitutes for the required observations above.
