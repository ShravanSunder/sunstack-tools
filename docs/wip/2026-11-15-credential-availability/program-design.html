Rust stops the unavailable work, not the whole run

The shared dispatcher owns whether a reached model step can execute. Graph walking still produces independent local results. A missing credential becomes a typed unavailable assessment or dependency gap, and the existing report projection retains findings while returning incomplete.

This realizes the execution contract. The current source reference is released 4e40a05b; its tree equals reviewed af978771. Shapes below are the proposed target, not compiled implementation.

Keep one owner for each decision

The host still resolves the credential once. Shared Rust owns admission, evidence, graph walking and model dispatch; the CLI and SDK remain consumers of that one execution. The change introduces no store, service, second runner or execution-policy flag.

Availability is a dispatcher policy, not a provider failure. The unavailable branch returns before a permit, request allowance, request ID or background task is reserved. The existing backend keeps its encoding, budgets, retries and receipt semantics for work that really can run.

Replace the dispatcher's separate mode and optional backend with one closed policy. Check that policy at a reached model boundary and again at the submission entry. Both use one policy owner; builders do not query the credential store.

This is the smaller realization of R1–R5: it preserves the existing host and provider boundaries. It costs explicit unavailable branches in rule, filter and selection handling. Revisit if a real caller requires the old acquisition order or credential resolution itself prevents independent work from progressing.

Make unavailable execution different from preparation

The policy owns mutually exclusive runtime states. An ordinary keyless run is never marked prepared and never receives a fake backend key. Needed endpoint/model settings are validated at the existing factory; a valid configuration with an unavailable credential can then acquire evidence.

After existing admission and checked-scope guards, the factory retains the current missing-key refusal for model-backed evidence listing/inspection, identified by the existing request's evidence_listing field. Otherwise it selects LocalOnly for no configured model work, Preparation for explicit prepare, Execution for a valid supplied credential, or CredentialUnavailable for ordinary rule evaluation after validating needed backend settings. A refused inspection never constructs CredentialUnavailable. Availability checks are pure reads of the per-run policy. LocalOnly reaching a model operation is an invalid internal request, not a guessed credential failure. Cancellation is checked before availability and again before actual task submission.

There is no transition from Unavailable to Submitted within the same run. Adding a credential requires a new ordinary invocation; no automatic retry, prompt, store write or resumption service is introduced. Existing keyed retries remain owned by the decision backend.

Keep existing host credential resolution once at entry. A lazy credential factory at the first ask could avoid some store reads, but adds a new callback and concurrent initialization policy across the core/host boundary. That is unnecessary for the accepted result contract. The current host lookup latency remains a cost; an actual non-returning lookup that prevents local work would reopen this choice.

A new unavailable result must carry its reason in Rust

Do not add an unavailable string and another optional reason to the current result bag. Keep common source/path/result identity fields, and flatten a closed ending tagged by the existing outcome wire key. The unavailable variant requires its reason; other valid existing JSON endings keep their current spelling and payload meaning.

The existing optional fields of older endings are preserved; this change does not broaden them or make an unavailable reason optional. Internal RulebookResult gains its own Unavailable variant with mandatory reason, actual walked path, answers read, optional reached step and affected field. FilterAnswerState and SelectionOutcome gain mandatory-reason Unavailable variants under their existing tags. Unavailable work has no inferred judgment basis.

Use a flattened ending to preserve valid existing CLI result JSON while strengthening construction of the new state. Rust callers switch on the ending and are updated in one cutover; no old Rust-field wrapper remains. The cost is explicit projection and exhaustive-match changes. A generated contract or serialization check that cannot preserve the selected shape reopens this structure before a build proceeds further.

Unavailable selection blocks unknown pieces without inventing them

Use the existing deferral mechanism to withhold unresolved selected candidates and propagate affected kind/file scopes. Extend its reason from preparation-only pending to a closed pending/unavailable distinction. Evidence owns only that dependency fact; it does not learn about credentials or depend upward on the rules crate.

EvidenceBuild keeps a per-candidate deferral reason, with Unavailable dominating Pending if both affect a derived field. FieldUnavailable gains SelectionUnavailable as a unit variant, preserving the existing Copy/value convention and lower-layer dependency direction. ModelView distinguishes SelectionUnavailable from SelectionPending. Walkers translate only a needed selected field into SelectedFieldUnavailable; a field not used by the path does not globally disable mechanical evaluation.

SelectionCount adds a full-width unavailable: usize count. Unavailable candidates do not increment asked, selected or not-selected. Per-file completeness explicitly requires zero unavailable candidates as well as the existing settled-accounting conditions, so missing child pieces cannot become conclusive absence. The counter is derived from actual selection entries, and new typed document validation checks its consistency.

Each affected kind/file is retained as a typed IncompleteReason::SelectionUnavailable carrying required evidence_kind, file and selection_kind. This is coverage identity, not a made-up final piece or provider request. Deduplicate each affected kind/file; retain all actual unavailable selection entries. A deterministic actual blocking selector supplies the scope's cause when several blockers exist.

A known rule behind an unavailable filter receives its own Unavailable result with FilterUnavailable identity, and the filter retains its actual unavailable answer. A binding to a not-yet-established piece uses the matching kind/file unavailable scope, not Unmatched or Stale by absence. Actual captured mismatching source still proves Stale under the existing identity rule. Known unavailable cases retain actual result links; unknown pieces get no invented result ID.

Keep dependency propagation in EvidenceBuild and report projection, extending their existing deferral and incomplete-scope structures. Do not create a second dependency graph, child-piece placeholder, pending request ID or inference receipt. This adds typed unavailable carriers, while existing configured kind dependencies remain authoritative.

Project one truthful partial report across the boundaries

Unavailable rule results and filter answers, plus unavailable selection entries/scopes, add typed incomplete parts. Existing status precedence remains cancellation, incomplete, finding limits, uncertainty, empty selection, clean. Counts never turn a gap into a pass.

UnavailableCounts has full-width rule_pieces, filter_folders, selection_candidates and evidence_scopes. One Rust counter derives them from canonical collections for the CLI summary and SDK projection; it does not add a new required root field to raw CLI reports. SDK reports expose unavailable_counts as a derived immutable snapshot. The SDK document decoder validates this new summary against those same facts; it never trusts a forged zero to erase unavailable work. Categories are separate units and are not summed into a misleading total.

Unavailable model work creates no request/attempt/receipt record just to fill a log. Its assessment retains path and source evidence. Already existing incomplete/provider NotSent and Run records keep their actual meanings. A real HTTP401/400/503 remains an observed provider failure; a disappearing native reply remains the existing effects-unknown failure and is never retried transparently.

Keep canonical ending collections authoritative and derive category counts in Rust. This gives SDK users direct typed counts without a TS classifier or duplicate mutable accounting. The new SDK summary's consistency check is part of its trusted document boundary; old counters are not redesigned.

Advance the SDK contract from19 to20 for new variants/fields, with the existing handshake and document mismatch refusal. Preserve valid existing CLI result encodings using the flattened ending. Do not add a legacy SDK decoder, dual execution mode or stored-report rewrite. Existing JSON/file storage remains the only persistence mechanism.

CaseBindingStatus and CaseOutcome gain a mandatory-reason Unavailable variant. A known uniquely bound unavailable result supplies its real result ID; an unresolved selection scope supplies no fabricated ID. Unavailable remains in selected denominators and is a non-success case under the existing bar/outer-exit policy; this does not redefine case exit as ordinary lint exit3. Native and SDK exact integer metadata regenerate from Rust, including new counts and any case IDs.

Contain the unavailable branch and observe real effects

Availability is immutable within one invocation. Independent graph walks continue, and the existing task owner drains actual dispatched work. No background recovery task, lock, new retry queue or cross-run state is added. Unavailable work does not consume model allowance, so it cannot starve an otherwise executable neighbor through fictitious accounting.

The existing owned loopback protocol is sufficient to falsify unintended dispatch and keyed-path request changes. It replaces the external provider answer, not Rust execution, actual HTTP submission or installed SDK decoding.

Why the alternatives were not selected

A lazy host credential factory at the first ask removes unnecessary lookups but adds an async host/core initialization boundary; D8 keeps that cost out. A backend that returns a synthetic failure after submission could avoid HTTP, but moves unavailable work through task/allowance/attempt accounting and broadens the decision protocol. D3 rejects that added coordination and keeps absence before submission. Retaining whole-run refusal or adding a policy flag does not satisfy the accepted default, so neither is a viable target under D1.
