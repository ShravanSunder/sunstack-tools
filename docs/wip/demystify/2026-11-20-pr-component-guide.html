Choose a Demistify component for a PR

Start with the question a reviewer has to answer. Write the answer in ordinary HTML, then add one view that makes the deciding relationship easier to see. The author writes the prose, diagrams, and examples. The components present that work.

What belongs in each part of the PR?

Reviewer question View to use What the author supplies
What changed and why? Opening prose. A callout when a release constraint or open question changes the next action. The current behavior, the proposed behavior, and the effect readers can check.
What outcome is required? A requirements heading with an exact anchor. A Tree when several requirements form a meaningful hierarchy. A user outcome, its source, and an ordinary link to the corresponding rule.
What must always hold? Rule prose with a small case table when the same outcomes must be compared. Preconditions, outcomes, and errors. Use one heading per question the reader needs to find.
How does it work? Sequence diagram for calls, state diagram for lifecycle, or a Board for ownership boundaries. Real owners, events, and branches, with the important exceptions in nearby prose.
Which option should we choose? Compare for aligned tradeoffs. Choice with optional Details when the owner needs to answer. The alternatives, consequences, recommendation, and one precise question. Cite the decision after it is confirmed.
Where should I look in the diff? File Tree for structure. Code or Diff for an exact excerpt with a line note. Real paths, the decisive change, and a link to the full review. A short excerpt can be enough.
How will we know it works? A planned-check section. Trace when ordered evidence has several stops. The action, passing observation, rejecting case, and proof boundary. Link a real run and revision when it exists.
What does the reader see? A figure for one capture. A linked Gallery page for multiple related states. Actual screen, state, viewport, and build. Use paired pictures only when a visual comparison answers a real question.
Where can I find the related sections? Pages for documents, Outline for the current page, Map for concerns, and Walkthrough for a useful reading route. Stable authored targets. Group linked passages around a question, such as how cancellation is enforced.

Follow one change from need to proof

Example: A previously queued job must stay cancelled when the worker drains the queue. The design explains which transition the store accepts. The check below covers the case where cancellation commits first.

In a multi-page version of this example, Pages would list Requirements, Specification, Program Design, and Verification. The Map groups the passages under cancellation. A Walkthrough asks which operation wins, then takes the reader from the rule to the diagram and check. A receiving agent can follow the same destinations by file and heading from its handoff.

Cancel before the worker claims the job

Let the worker drain the queue. The job must stay cancelled and the handler must have zero entries. A build that keeps the status but calls the handler fails.

After running the check, link the observed result and exact build to the planned check. The same trace structure can present the receipt when a result exists.

How should an agent get the component instructions?

Keep the component chooser in the presentation skill. Design skills describe what to explain and send the author there. The Demistify guide owns exact markup for the selected runtime.

Option What an agent loads What we maintain
Published references today The release's entry guide and the selected component files over HTTPS. Demistify publishes one source. A cold read needs network access. Guide text enters the model context whenever the agent reads it.
Versioned copy in the installed skills A local component index and just the references selected for the page. Older or custom bindings use their own guide. Demistify remains the source. A release sync copies exact references and opens a reviewable Sunstack update.
Render the manual inside Sunstack A local skill index and the same selected text. A rendered manual serves people browsing it. A render step and its output. It helps humans browse, while agents still need the source text or an equivalent retrieval interface.

Proposed. Vendor the versioned reference files and read them on demand. Render examples for people separately. When a page uses a newer release or a different binding, use that binding's guide. Compare how much text an agent actually loads for the same PR before claiming a token saving.
