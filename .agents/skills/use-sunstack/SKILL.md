# Use Sunstack

Evidence before judgment: an authored standard or supplied taxonomy determines what source evidence means, and an operation's actual status limits the claim. Acquisition can itself ask a model when selection is configured, so execution authority and budget apply before acquisition. Restored SDK values preserve original data, including any status and provenance their root carries; decoding neither executes nor authenticates them.

1. Name the requested artifact and claim. Choose inspection for source pieces and locations, evaluation for decisions against an authored standard, or the SDK codec for saved typed data. For repository work, identify the checked root and scope; for classification, identify who supplied its policy.
2. Inspect configured selections and questions before acquisition. Apply the conversation's existing execution authority and budget; an ambient credential is availability, not permission. IF a required paid effect is uncovered by that authority, follow the host's existing permission policy and continue the relevant keyless work.
3. Read the interface that matches the selected route and installation before authoring:
   - IF using the CLI, load [the CLI guide](../../../crates/sunstack/README.md), compare it with `sunstack --version` and `sunstack lint --help`, and return the supported command, complete configuration dependencies and output interpretation. Installed help owns callable syntax; use repository semantics only against a matching binary.
   - IF writing a typed program, load the README and selected example from the resolved installed `@sunstack/sdk` package; use [the repository SDK manual](../../../packages/sdk/README.md) and its examples only against the matching verified repository candidate. Compare the package version and `contractInfo()` with the selected documentation, and return the complete values required by the API, strict compile command and outcome handling.
   - IF an installed operation is missing or versions differ, report both versions and the unavailable flag or export, then use matching supported guidance or the verified candidate already authorized for the task. Do not invent an export or install a replacement to make the recipe fit.
4. For a typed program, author complete SDK values against the exported Rust-derived types with `satisfies`, literal unions and `as const` where narrowing is needed. For evaluation, admit definitions before execution and proceed only on valid admission. Direct SDK inspection performs its own admission and can use an empty rulebook collection; handle its returned outcome without loosening ordinary evaluation admission. Compile a typed program strictly and run it through the actual SDK; execute the real command for CLI work.
5. IF saving or restoring known SDK values, follow the selected SDK manual's `serialize`/`deserialize` recipe and return the saved artifact plus the narrowed restored root, retaining any status and provenance it carries. Narrow both outcome and payload tags, leave file storage to the caller, and admit a restored configuration before evaluation. Use the owning codec instead of recreating numeric conversion; a decoded report is original data, not a new or authenticated check.
6. Deliver the requested artifact with the actual command, tool/package identity and result. For a typed program, include both strict compile and real run results; for CLI work, include the real command result. Report the actual outcome/status, selected scope, file and piece counts, relevant source locations and incomplete reasons. Keep extracted facts separate from policy judgments, and retain uncertainty, failure and zero or partial coverage in the conclusion. A clean listing means evidence work completed; it does not establish absence of violations.
